# 秘書による目的判断と自律継続

## 責務と不足していた部分

人間と秘書は目的・合意・許可範囲を会話で共有する。秘書はその範囲でリーダーに依頼し、返された成果を評価する。リーダーは実行計画・工房管理・技術品質と結果提出、工房は具体作業を担う。

従来は提出結果を会話へ配送すると実行graphがcompletedになるが、秘書の採用記録はなかった。回答が正常終了すると通常通知になり、完了後の修正は別の無関連jobになっていた。PR130は表示位置を改善したが、この責務の欠落は解消していなかった。

## 最小の追加

実行graphの意味と過去結果は変更しない。同じ会話内に目的IDと明示判断を追加する。

- 新jobのpurposeIdはそのrequest ID。継続jobは同じpurposeIdとcontinuesRequestIdを持つ。
- c.purposeDecisionsに資料deliveryId、対象request、actorRunId、理由、kind、必要な具体質問、継続先、判断時の人間入力sequenceを保存する。
- decide accept/questionは既存の入力受付・正常終端を照合して初めて有効になる。正常応答だけで採用を推測しない。
- continuesRequestId付きjobは元の許可を同じrunId/quoteで参照し、元の結果と目的versionを照合する。継続判断と関連jobを同じ保存境界で作る。外部操作の再送ではなく残作業の指示を渡す。
- 実行中の仕事へのamendは従来どおり。人間への質問後のamendは明示的な再開記録を残す。
- 達成報告後の追加修正には、その後に正式配送された人間入力reopenRunIdを指定する。同じ許可の範囲を越える新目的は別job。元許可を拡張する機能ではない。
- 原子的な継続/補足は秘書返答の成否にかかわらず実行済みの受付として保持する。accept/questionは秘書失敗・未確認・判断中の後着入力では確定しない。

APIが検証するのは発話・許可引用・資料・actorの由来と状態であり、自然言語の権限範囲そのものを機械的に判定するものではない。意味上の許可判断は正式rulesで秘書に課す。相談を自動的にjobへ変換する処理はない。

## 表示と通知

関連する一つの目的について、秘書の評価中/明示達成/具体質問/停止/継続先の実行状態を回答直下に表示する。継続jobごとに人間へ内部工程を数えさせない。新しい仕事資料への未判断の回答・継続だけの回答はprogressとして折りたたみ、通常通知しない。明示accept/questionが正常終了すればreply。別目的を同時に継続していても具体質問や達成報告を隠さない。displayによるreply指定だけで評価を迂回しない。

人間向けの質問は秘書が具体的に記録したものだけ。リーダーから秘書への質問を人間の判断待ちと推定しない。人間の新しい入力だけで質問が解決したと推測せず、秘書の明示amend/判断を待つ。

旧完了graphに明示判断がない場合、後付けで採用済みにせず秘書の確認待ちとして扱う。旧回答や通知を消さず、仕事を自動再送しない。旧配送runにはrequiresPurposeDecisionを遡及追記しない。

## 競合・復旧

会話の固定lock/保存rollback/operationId冪等性を利用する。二重継続、古いversion、未配送資料、別会話、元許可の差替え、後着人間入力を拒否。判断中に人間入力が来た場合も、完了を推定せず再評価にする。失敗した判断は後続の正式会話runから再評価でき、完了済み工房実行を再送しない。再起動後も目的と判断、通知抑制、原子的な継続を保持する。

未評価の新目的を持つ秘書の削除・Project変更は拒否。通常のruntime移行や旧履歴の読取は変更しない。

## 運用適用

固定startup()は変更しない。正式動的rulesのrevision、配送資料、CLI/HTTP APIを更新する。既存セッションにプロンプトファイル変更が適用済みと称しない。新しい配送は既存契約に従って最新rulesを読み、新APIを利用できる。今回は追加の停止/旧データ削除/Agent移行を必要としない。

検証は隔離サービス、実型graph/native受付fixture、HTTP、PC/スマホで行う。本番の既存仕事を試験として再実行しない。実モデルの自然言語判断品質を保証するテストとは区別する。
