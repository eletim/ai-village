# 起動時の参照検証と履歴整合性

## 依頼の隔離

`request-integrity.mjs` が既存の移行処理より前に依頼グラフ全体を検査する。
ルート作業、親作業・循環、作業の送信一覧と現在の送信、送信の依頼／作業／Agent、
初回／最終／報告元の送信、モデル内の送信一覧、委任・結果配送・補足・再試行・完了申告の参照を照合する。
削除済みでも保存されたAgentが存在すれば有効な参照であり、稼働中であることは要求しない。

参照が壊れた依頼には `integrity: {version: 1, reasons: [...]}` を付ける。
元の作業・送信・状態モデルを書き換えて辻褄を合わせず、画面/API上は「要確認」として投影する。
隔離した依頼は自動送信、観察による送信状態更新、子結果配送、報告作成、限定再試行、通知から外す。
`requests get` と画面の「要確認の依頼」で参照名とIDを確認できる。
正常な依頼の処理は継続する。既存の受付不明を自動再送する変更はない。

壊れたグラフに対して人間の再試行・完了扱い・取り下げを実行しても別の記録を壊す可能性があるため、
隔離中はこれらの操作も拒否する。記録のバックアップを取り、根拠を確認して参照を修復し、
再起動すると全体を再検証して隔離を解除する。自動修復や専用修復画面は今回の範囲外。
孤立した送信（依頼自体が存在しないもの）も送信対象にしない。
JSON自体の破損・未知の保存形式・重複する主IDなど、依頼の同定が安全にできない破損は引き続き起動拒否する。

## ネイティブ索引

履歴整合性の導入時はPARSER_VERSION=7。現在は入力の一対一重複排除を含むversion 8（[入力照合](input-envelope.md)）。既読領域の1MiBごとのSHA-256をSQLiteチェックポイントと
独立したsource proofに保存する。受付判定と中央部分の巡回監査を分離する。

各読取りでは、同一ファイル・サイズ減少なし・既読の先頭/末尾4KiBと境界チャンクの一致を確認する。
境界チャンクは全体を検証してから追記分を含むハッシュに更新するため、端数チャンク内の改変を
新しい正しいハッシュとして取り込まない。境界が一致する追記は追加分をパースし、監査完了を待たず受付情報を返す。

中央部分の監査は毎呼出し最大32MiB（別途境界1MiB以下）を進める。
一周の対象チャンク数を開始時に固定し、追記・stat更新では進捗をリセットしない。
一周終了後に次の周回で追加チャンクも含める。追記が止まっても巡回は継続する。
これにより100MiB以上の成長中の履歴でも、監査を理由とする受付待ちは発生しない。
小さい履歴は一回で全領域を検証する。chmod等で内容が変わらなければfileIdentityは維持する。

不一致・切り詰め・ファイル置換を検知すると、新しいfileIdentity/generationで索引を再構築する。
JS replicaも既存のgeneration切替で破棄・再同期する。再構築途中の受付は返さない。
読取り処理の最中にファイルが変更された場合も、その読取り結果は公開せず次回確認する。
UTF-8・部分行・圧縮要約は従来どおり。旧パーサーの索引は実ファイルから再構築する。

限界: 中央の改変は遅延検知であり、**検知前に下した受付・終了判定は取り消せない**。
持続する改変は、そのチャンクを再び巡回するまでに検知する。一周は対象サイズ/32MiBを切り上げた呼出し数。
既に巡回した部分の改変は次の周回になるため、タイミングによっては周回境界をまたぐ。
書換え後に監査より先に元に戻された一時的変更や、管理者が記録・索引の両方を改変する攻撃は保証対象外。
初回構築・改変後の再構築・大量の未読データは従来のバッチ制限による待ちがある。
