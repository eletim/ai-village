# 起動時の参照検証と履歴整合性

## 依頼の隔離

`request-integrity.mjs` が既存の移行処理より前に依頼グラフ全体を検査する。
ルート作業、親作業・循環、作業の送信一覧と現在の送信、送信の依頼／作業／Agent、
初回／最終／報告元の送信、モデル内の送信一覧、委任・結果配送・補足・再試行・完了申告の参照を照合する。
削除済みでも保存されたAgentが存在すれば有効な参照であり、稼働中であることは要求しない。

参照が壊れた依頼には `integrity: {version: 1, reasons: [...]}` を付ける。
元の作業・送信・状態モデルを書き換えて辻褄を合わせず、画面/API上は「要確認」として投影する。
隔離した依頼は自動送信、観察による送信状態更新、子結果配送、報告作成、限定再試行、通知から外す。
`requests get` と画面の「要確認の依頼」で参照名とIDを確認できる。
正常な依頼の処理は継続する。既存の受付不明を自動再送する変更はない。

壊れたグラフに対して人間の再試行・完了扱い・取り下げを実行しても別の記録を壊す可能性があるため、
隔離中はこれらの操作も拒否する。記録のバックアップを取り、根拠を確認して参照を修復し、
再起動すると全体を再検証して隔離を解除する。自動修復や専用修復画面は今回の範囲外。
孤立した送信（依頼自体が存在しないもの）も送信対象にしない。
JSON自体の破損・未知の保存形式・重複する主IDなど、依頼の同定が安全にできない破損は引き続き起動拒否する。

## ネイティブ索引

PARSER_VERSIONを7へ更新。既読領域の1MiBごとのSHA-256を、SQLiteチェックポイントと
独立したsource proofに保存する。mtime/ctime/サイズの変化は「変更確定」ではなく「バイト検証が必要」の合図。
chmodなどのメタデータ変更だけならfileIdentityは維持する。

変更がなければ先頭・末尾とstatの確認（および最後の端数チャンクのハッシュ）だけで済ませる。変更時は既読領域を1回最大32MiBずつ検証し、
検証中は `available:false`、入力・終了情報は空で返す。検証の途中で再びstatが変われば最初から確認する。
不一致・切り詰め・ファイル置換では新しいfileIdentityとgenerationで再構築する。
JSのreplicaは既存のgeneration切替で破棄・再同期され、検証待ちの古い受付は返さない。
追加分のパースとハッシュ作成は従来同様に範囲を限定する。UTF-8、部分行、圧縮要約の処理は変更しない。
旧パーサーの索引は再構築する。ハッシュ導入前の中央部分については過去の内容を証明できないが、旧索引の入力を再利用せず実ファイルを読む。

全領域の任意の変更を見逃さないため、追記でもstat変更後の既読領域の検証総量はO(履歴サイズ)。
毎回のポーリングで全量を再ハッシュせず1回の量を制限する代わりに、巨大な履歴・連続書込み中は受付判定が遅れる。
ローカルファイルシステムのstat（特にctime）が書込みを反映する前提。管理者が記録と索引の両方を改変する攻撃の検出機構ではない。
