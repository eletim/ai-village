# 自分の仕事の単発再開予約

## 目的と最小変更

Agentが「30分後に稼働を確認する」など、仕事に必要な再確認時刻を自分で選べるようにする。従来は子結果・追記・期限通知による再開だけだった。期限の変更権限を拡張するのではなく、現在の依頼nodeに `selfResume` を1つ保持する。時刻到来は既存RequestReportsの単発タイマーで処理し、既存inboxとSQLite wakeupへ渡す。調査方法、追加作業、成果の採否はAgentが判断する。新しい巡回、業務フロー、監督Agent、報告審査は追加しない。

## 正式操作と待機契約

CLI `requests selfResume JSON`、API `POST /api/direct/requests/selfResume`:

```json
{"humanRequestId":"現在の依頼ID","workId":"自分の仕事ID","actorRunId":"現在runID","operationId":"一意な操作ID","expectedVersion":0,"at":"2030-01-01T12:30:00+09:00","text":"稼働状況を確認し、観測した結果に基づいて判断する"}
```

実際には現在より未来の時刻を指定する。初回versionは0。以後は `requests get` の `requestGraph.nodes[].selfResume.version` を読む。同じ操作の再送は同じoperationId・同じ内容。別の変更は最新versionと新operationId。`at:null` は取消。置換は旧予約を取消履歴に残して新しい予約IDを作る。発火・消化・完了による取消もversionを進めるため、競合時は読取して再判断する。現在の受付照合済みrunning work runと担当者だけ操作可能。報告phase、他のwork、古いrun、未受付/受付不明は拒否する。

予約の後は **`respond` で今回対応したinputsとresultsを明示し、通常回答を終える**。leafでも予約中はactiveの待機になり、成果提出/人間通知を先走らない。予約だけでは入力対応の申告を代行しない。残る入力があれば既存の入力集約に従って再開する。予約を待つ回に `finish` を使わない。finish申告後の予約作成は拒否する。

`finish` が当該runの正常終了で確定すると予約を取消す。実行中のfinish申告だけでは取消さず、失敗・中断・不明の申告は確定しない。人間による依頼の完了/取り下げも予約を取消す。予約は報告期限/完了期限を一切変更しない。期限が先に来た場合も既存の報告義務は残る。

## 配送、競合、永続化

- `selfResume.current` が時刻・内容・作成run・予約ID・状態の唯一の正本。`history` は置換、取消理由、配送、入力対応の監査記録。既存graph v3の任意フィールドであり、旧依頼の保存移行や本文書換えは不要。
- 発火は予約IDをそのままinbox IDにする。状態をdeliveredにする変更、`source.actor=program` の入力追加、SQLite wakeupは既存の保存単位で確定する。内部通知が人間の訂正へ昇格しない。
- 実行中には割り込まず、正常終了後に未対応の子結果/追記と集約する。既に送信したrunを未送信扱いに戻さない。
- 予約置換/取消は旧IDの未処理入力をretiredにする。完了時は未送信の予約起因inbox runも取消し、不要な起動を防ぐ。既に送信済みなら停止・巻戻しはしない。最新inputsでretiredを確認し不要な確認作業を繰り返さない。
- failed/interrupted/unconfirmedは予約だけで再実行しない。時刻到来の入力は保存されるが、既存の復旧権限と終了照合が必要。正常な終了と外部作業の成功は別であり、村内の単一配送は外部副作用のexactly-onceを保証しない。
- 予約変更と発火は依頼単位/graph lockで直列化し、versionで競合を検出する。保存失敗は状態とreceiptをrollbackし、発火は既存バックオフで再試行。再起動時は保存されたscheduled時刻からtimerを再構成し、遅延時も一度だけ入力を作る。新しいポーリングはない。
- 画面の「依頼の構成・分割」で時刻、確認内容、予約/配送/取消の状態を閲覧できる。Agentがまだ実行中なら予約あり、正常終了後なら再確認待ちと表示する。人間用の新しい変更フローは追加しない。

固定bootstrapとreport仕様は変更しない。可変work仕様・CLI helpに操作とrespond待機手順を追加するため、work rulesRevisionは変わる。既存の仕様取得/旧セッション互換経路で更新される。

## 親の実AI受入手順（本番の既存Agentを使わない）

1. 専用ポート、使い捨て状態dir/Project/作業dir、新規Agentの隔離村を準備。通知は無効、既存サーバー再利用は禁止。専用状態dir・ポート・revisionをhealth/起動記録で確認する。
2. 使い捨て作業dirに `probe.txt` を `before` で用意。「このファイルを60秒後に読み直し、変化を観測して結果を判断。予約して待機し、再開後に確認する」と依頼する。Agentが新work仕様を取得しselfResume→respond(inputs/results)→正常終了することを確認する。
3. getで同じwork/担当ID、selfResumeのscheduled・時刻・確認内容、active/waiting、元の期限が不変、人間の完了通知なしを記録する。待機中に検証者がファイルを `after` に変更する。人間の再開指示は送らない。
4. 時刻到来後、同じworkで新runが1つ発行され、予約IDと同じinbox ID、source program、正常な受付照合を確認する。Agentが実際にファイルを読み、before/afterの変化から成果を判断し、inputs/resultsを明示してfinishし正常終了することを確認する。自己申告だけで読取成功と判定せずCLI/nativeのツール記録も保存する。
5. 別の隔離依頼で、発火前finish、取消、実行中に時刻到来、子結果/追記の同時到着を確認する。二重起動・期限変更・不要な完了通知がないことを確認する。失敗/不明の検証では受付不明を自動再送しない。
6. 証拠は依頼/予約/入力/run ID、時刻、操作receipt、native記録、ファイル内容、UIを保存する。秘密や個人情報をcommitしない。テストAgent/状態は検証後に整理する。

工房側は機械テストと隔離HTTP/ブラウザまで。実AIによる判断品質・SSH・実運用の時刻精度は親の受入対象。タイマーは最善努力の到来通知で、プロセス停止中の指定時刻実行を保証しない。

## 反映・ロールバック

親レビュー後に通常の整合バックアップと反映手順を使用する。旧データには予約がないため移行なし。予約を作成した後に予約未対応の旧コードへ戻すと待機/配送保証を失うので、そのまま運用しない。現行コードで予約状態を確認し取消/完了または予定の引継ぎを済ませるか、反映前の整合バックアップへ戻す際に以後の外部効果・入力を別途照合する。過去の外部操作の再実行はしない。
