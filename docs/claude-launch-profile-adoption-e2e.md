3. Donor remained unused/unspoken. A browser loaded the isolated Village normally, received its own human-UI cookie, and invoked the existing guarded prepare/adopt APIs. Both prepare and adopt returned HTTP 200. No authentication bypass or production credential extraction was used.

## Exact blocker

PurpleMux still reports `alive: true`, `cliState: idle`, `lastEvent.name: session-start`, matching receipt/startup profile/session, with no last user input. Village reports process alive but activity unknown, `canSend: false`, reason `接続・稼働状態を確認できません`. Both new runs remain `queued` with no `dispatchAttemptedAt`.

`server/direct.mjs` observe's `freshClaude` condition currently rejects any prior `dispatchAttemptedAt` for the **Agent ID**. Adoption deliberately preserves the Agent's normally completed old-session history. Thus the fresh runtime loses freshClaude eligibility after adoption even though none of its own session's inputs has been sent. `runtimeObservation` then fails closed for an unavailable native transcript without freshClaude evidence. This is reproducible on the first lifecycle without restarting; it is separate from the previously documented restart/session-start-event limitation.

## Minimum proposed follow-up (not implemented)

Retain generic canSend/unknown protection. Bind fresh-session qualification to a verified adoption receipt and exact current runtime identity (workspace/tab/session/profile/startup contract), instead of treating all historical Agent runs as current-runtime sends. Preserve all run/history records. Never infer new-runtime innocence from a missing sessionId: current in-flight/unknown attempts or unclassifiable send evidence must still deny. A migration receipt alone is insufficient: re-observe live idle, exact session-start identity, no native inputs/turns, no newer/current-runtime dispatch, no setup/permission state, valid launch evidence, and current startup contract. Scope proof to the adopted runtime; do not broadly allow every new session or relax restart holds. Review any previousSession/native-unavailable guard together with this qualification rather than deleting it.

Add targeted tests for normally ended old-session history, retained queued work, first adopted dispatch, current/unknown attempts, reused/mismatched runtime identities, lost startup event/restart and native record loss. Then repeat only this failed adoption-to-first-conversation path for both models. Do not speak to a donor before adoption. Parent approval is needed before changing product safety logic.

## Approved scoped fix and new acceptance (2026-11-25)

The follow-up adds `server/adopted-fresh-runtime.mjs`. Adoption may record a versioned `freshProof` with old/new workspace/tab/tmux/session/profile/contract identities, exact startup event, and IDs plus SHA-256 digests of confirmed old sends. Digests cover the run model/facts, input/session binding, instruction/output and normal-terminal fields, excluding unrelated delivery notification bookkeeping. Missing accepted session, mixed identity, missing native input/normal turn, unclassified run, or unproven history yields no exception. Only a profile-bearing formally adopted runtime can use this proof; ordinary no-profile/non-adopted behavior does not gain permission.

The adoption transaction recomputes the proof immediately before saving the swap. The first fresh observation requires current live idle/session-start, no setup/permission/native use, exact receipt/startup/profile/fixed contract and unchanged historical sends. Removed/modified old history and any new send invalidate it. Before the durable dispatch intent, the same proof is rechecked after asynchronous instruction verification. Existing per-Agent locking excludes adoption/dispatch interleaving; the proof is not a replacement for lifecycle controls or native acceptance. Once a current-runtime send exists, this exception no longer applies. Native-file loss, previousSession checks and restart without session-start remain closed.

New evidence is under `model-implementation/adopted-fix/`. Both servers had dedicated HOME/config/native directory, state, cwd and TMUX_TMPDIR from initial spawn; ports were 57297/50249. New source/donor pairs were made through Village's API. Both donors remained unspoken until adoption. Both prepare/adopt operations succeeded; both subsequent conversations on the original Agent/conversation IDs were accepted and ended normally, with one dispatch each. Old run objects remained unchanged. Native assistant metadata separately confirms source and adopted `claude-sonnet-5/high` and `claude-opus-5/high`, with `end_turn` and no tool calls.

Sonnet's adopted response also said it regarded the supplied village instruction blocks as possible injection and did not execute them. The raw output is preserved: this confirms transport/identity/normal response, **not general compliance with Village operational instructions**. Opus returned only the requested short confirmation. No donor inference occurred before adoption; startup effort remains argument evidence, separately from actual response effort.

Regression covers proof identity/history mutation, missing session, unclassified/current sends, used native data, permission/setup, lost startup event, contract changes, queued retention, one dispatch, save rollback, same-operation receipts, pre-save history change and restart. Initial integrated fixture failed 7 cases because its native lookup only recognized the original synthetic session IDs; overriding its native reader with the same in-memory snapshots fixed the fixture without changing product safety. A review of the initial helper also found its empty-send fast path could overlook deletion of all proven old sends; this was fixed and a removal regression added before live testing.

Deployment: PurpleMux launch-profile commit `03e1c101` must be available first; then Village launch-profile implementation plus this scoped fix. This task changes Village only. No existing Agent/session/settings are migrated automatically. Old receipts without `freshProof` retain the conservative behavior. For rollback, stop new migration operations and restore the prior Village version: already saved proof fields are inert data, histories remain, and unspoken adopted sessions may again hold safely. Do not replay a queued/unknown external operation as a rollback shortcut. Parent owns deployment, existing Agent migration and PRs; worker performed none.

Final hardening re-observes the adopted runtime after asynchronous contract verification and snapshots nested identity values independently. Both are covered by mutation tests. The final-product real-AI check is recorded separately in `adopted-fix/final-live/` (new isolated ports 57263/42599). Only that disposable Village server was reloaded before adoption to load these final changes; PurpleMux was not restarted and retained its live session-start events. This is not evidence that losing the startup event on a PurpleMux restart is safe. The earlier run without any restart and the previous failing restart evidence are both retained.

This exception intentionally does not certify arbitrary migration chains, stopped targets without readable native proof, older receipts lacking proof, or history with absent/mixed session identities. Those remain held rather than guessed. External processes can always change after a read-only observation; the immediately refreshed identity plus transaction recheck narrows the race, while durable send intent and existing acceptance correlation retain the no-automatic-replay rule if transport becomes uncertain.

Final result: both final-product adopted conversations were accepted, normally terminated and had exactly one dispatch, preserving the original Agent/conversation IDs and old run objects. Both native model/effort pairs matched; final responses were the requested short confirmations. Related Node tests: 79 passed. `npm run check`, `npm run typecheck`, `npm run build` passed.
