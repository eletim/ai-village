# 村の状態モデル — 段階0・1と段階2の接続

人間承認済み方針を、事実・申告・判断を混同しない状態処理として整理する。
基準は `origin/main` の `74dc1f9`（PR #57 マージ済み）と
[村の思想](concept.md)。Agentを信頼し、出力形式で縛らない。
**自然言語の出力・達成度を解析して状態を動かすことは禁止する。**

段階0・1（PR #58）は設計と未接続の純粋関数。段階2は送信だけを接続する。
**以下の依頼・Agentの完成形は段階3・4の設計であり、まだ現行動作ではない。**
段階2の互換範囲・移行・反映方法は [段階2の運用メモ](state-stage2.md) を参照。
このブランチからmainへのマージ・本番反映は行っていない。

## 判定者と保存するもの

| 判定者 | 役割 | 禁止事項 |
| --- | --- | --- |
| ① `program` | 観察事実を伝える。report・resultの送信を作成する（それ以外の新規送信は禁止） | 出力の意味から成功を推測しない |
| ② `agent` | 委任を作成する、委任ありの完了を申告する | retry/resume/cancel、CLI結果の変更、依頼の取り下げ |
| ③ `human` | 新規依頼、取消、やり直し、取り下げ、完了扱い、起動・停止 | nativeの事実を「正常終了」に改ざんしない |

事実、Agentの申告、人間の判断を別のデータとして保存する。完了扱いでも失敗した
送信の結果を残す。取り下げ後に届いた終了記録や申告も保存し、依頼は再開しない。
申告は入力照合前でも受け付け、重複を含め履歴に残す。未照合は証拠待ち、確定した
不一致は要確認とする。子結果の acknowledge は新モデルに存在しない。

`Actor` とイベントごとのliteral型、および `*Authorities` 表で権限を表現する。
型を迂回したJavaScript呼び出しも判定者を検査する。ただしactor文字列は認証ではない。
段階2以降のAPI境界で本人/操作権限・ID・スキーマを検証し、認証済みイベントにする。
同様に、①のイベントを作る観察アダプターには根拠の検証責任がある。

## Agent：観察から導く7状態

| 日本語 | コード | 条件・遷移 |
| --- | --- | --- |
| 起動中 | starting | ③の起動指示、まだ観察なし |
| 待機 | idle | ①が接続・プロセス・待機を確認 |
| 実行中 | running | ①が実行中を確認。補足能力も観測値 |
| 入力待ち | input-needed | ①が権限確認など入力待ちを確認 |
| つながらない | unreachable | 接続断、プロセス/活動が確認不能、初期再観察待ち |
| 停止中 | stopping | ③が停止を指示し、①の終了確認待ち |
| 終了 | ended | ①がプロセス不在を確認 |

起動中→待機、待機⇄実行中、実行中→入力待ち、接続断と復帰は①。
入力待ちに③が回答し、①が変化を確認して実行中へ戻る。回答の文面はモデルに渡さない。
停止は③の指示と①の確認を分離する。開始・停止指示は実行を伴わない意図であり、
副作用は将来のアダプターが担当する。観察スナップショットは最新値、過去の
観察監査ログは将来の保存層が保持する。

送信可は待機のみ。待機キューは起動中・実行中・入力待ち、補足は実行中で
観測された能力がある場合だけ。つながらない/停止中/終了は送信不可。
`sendControls(agent)` は依頼を引数に取らず、報告待ち・要確認・reportPendingを
ボタンに混ぜない。それらは依頼欄に表示する。

### 「人間の操作で出口がある」と物理終了の区別

依頼は常に③の取り下げ・完了扱いで終えられる。未送信は取消、送信後は③の
追跡打切りで「確認できず」に終えられる。追跡打切りはCLI停止や成功を意味しない。
Agentについては③の停止指示→①のプロセス不在確認という出口を用意するが、
接続できないPCの実プロセス終了を人間の操作だけで保証することはできない。
ここを強制的に「終了」にするのは観察から導出する原則に反するため行わない。
必要なら段階4で「一覧から管理対象を外す」という判断を物理状態とは別に設計する。

## 送信：5状態、終了結果4種類

| 状態 | イベント・判定者 | 次の状態 |
| --- | --- | --- |
| 未作成 | ③の新規送信 / ②の委任（phase=work） | queued（送信待ち） |
| 未作成 | ① prepare-report（phase=report）/ deliver-result（phase=result） | queued。人間を偽装せずprogramが作成 |
| queued | ③取消 | cancelled（未送信の取り消し） |
| queued | ①Agent待機確認＋送信記録 | sent（送信済み） |
| sent | ①native user入力で目印とsessionを確認、競合なし | running（実行中） |
| running | ①同じsession/turnの終了記録 | ended（正常・失敗・中断） |
| sent / running | ①session変更、目印なしで回終了、時間切れ | ended（確認できず） |
| sent / running | ③追跡打切り | ended（確認できず、人間の判断を別記録） |
| ended（正常以外） | ③やり直し | 元送信は不変、新IDのqueuedを作る |

目印はPR #57の `ai-village-run-<id>` をnative入力から照合する。包装、本文の
`<pasted_content>` の加工、出力文の内容には依存しない。目印の部分一致・競合入力・
別session・別turnでの終了を拒否する。段階2のアダプターでは既存のファイル同一性、
cursor、重複入力、steer境界チェックも必ず維持する。新関数単体はJSONLを読まない。

未知の送信結果を自動再送しない。確認できずは**終端**であり `blocksInput=false`
などの補助条件で止まらない。②は送信結果を変更できない。結果の変更ではなく
新しいIDの送信を作るため、元の失敗や副作用の可能性を履歴から失わない。

自動再試行の例外は①が確認した `server_overloaded` のみ。最大2回・最初の失敗から
10分未満、Agent待機、native終端の境界確認、子作業のないrootが条件。
report・result・子作業・委任あり・中断・確認できず・他エラーを自動再試行しない。
段階1は回数/時間を検証し、時計や再試行タイマーを持たない。現在の30秒/120秒の
待ち時間と監視スケジュールは段階2のアダプターで維持する。

## 依頼：3状態、要確認は進行中の印

| 状態 | 条件・判定者 | 結果 |
| --- | --- | --- |
| 未作成 | ③新規依頼 | active（進行中） |
| active、委任なし | ①最初の送信が正常終了 | completed（完了） |
| active、委任あり | ②まとめ役の申告＋①その送信の正常終了、子送信がすべて終端、未配送なし | completed |
| active | ①失敗・中断・確認できず、申告との不一致 | active＋review（要確認） |
| active＋review | ③完了扱い / やり直し / 取り下げ | completed / 新送信のactive / withdrawn |
| active | ③取り下げ | withdrawn（取り下げ） |
| completed / withdrawn | 新しい質問 | 新しい依頼。元依頼は再開しない |

委任なしの通常処理は完了申告不要。手動やり直しの場合はその新送信の正常終了が対象。
委任ありはまとめ役の申告と、その申告した送信の正常終了を必須にする。子作業が
未終了なのにまとめ役が完了した場合や、子作業の失敗は要確認として残す。
失敗の後に別の正常終了が来ても無関係な要確認を自動消去しない。人間のやり直しは
対象送信の印のみ解決する。全体を完了扱いする場合も元事実は維持する。

報告モードでは、作業の条件成立後に①がreport送信を用意し、依頼は進行中のまま。
reportは普通に正常終了すれば完了し、追加の完了申告は求めない。report失敗も要確認。
「できた・一部・できなかった」は②の自然文の評価であって、この処理への入力ではない。

### 進行の不変条件

`checkProgress(request)` は進行中の依頼が次のどれかを満たすか検査する。

1. queued / sent / running の送信がある。
2. 実行可能なプログラムの次手順がある（`nextSteps` の prepare-report / deliver-result）。
3. 要確認の印がある。

どれもなければ `stalledRequests` が検出する。通常のreconcileは `needs-decision`
を付け、遅い有効な申告等で進めるようになればこの導出した印は再評価する。
失敗や人間の判断待ちの印は引き続き勝手に消さない。移行で自動完了を控える場合は
`legacy-needs-decision` を付け、無印の進行中に取り残さない。
報告を作れる移行済み依頼は自動完了も自動送信もせず、prepare-reportを次手順に残す。
**段階2の接続時・再起動時にプログラムがnextStepsを列挙し、保存・排他の下で消化する。**
送信先Agentが削除済みなど実行不能なら、アダプターは要確認として人間に提示する。
純粋モデルの「次手順あり」は外部PCが実行可能だという保証ではない。

### 子結果の配送

プログラムが新規作成できるのはreportとresultのみ。resultは子送信が終端に
なった後、結果（正常・失敗・中断・確認できず・未送信取消）にかかわらず作成可能。
`resultOf` は元の子送信IDで、同じIDに対する配送の作成は一度だけ。
`recipientRunId` は親の現在の会話位置を示し、そこから将来の接続層が親Agentを解決する。
配送は親側の後続送信として扱い、親の親子関係を引き継ぐ。root宛てならrootの
現在送信も配送へ進める。ネストした委任でも受取人と元の子を混同しない。
配送の送信・照合・終了は普通のrunと同じ。配送が確認できずなら要確認、
自動再配送はしない。人間が別IDでやり直す場合も元resultOfを保持する。
作成済み配送を失敗・取消後に再びdeliver-resultで作り直すことも拒否する。
並行イベントの同時作成防止は段階2の保存層で直列化する必要がある。
結果を受けた親の回で完了を申告できる。全子送信の終端を確認し、acknowledgeは要求しない。

workは独立状態を持たない。送信列の `parentRunId` と `retryOf` で親子・後続を保持する。
通知配送、表示の折りたたみ、画像、添付、travelのデータは状態数に混ぜず、既存情報を
失わずに別の責務へ移す。段階1の移行は元JSON全体も `legacy` にコピーして保持する。

## 現行→新モデルの対応（移行時）

現行はAgent 11＋run 12＋work 6＋request 4で約33種。新モデルの主状態は
Agent 7＋run 5＋request 3＝15種。終了結果4種類や再試行予算、事実の識別情報は
判別共用体のデータであり、新しい独立したライフサイクル状態にはしない。

| 旧Agent | 新しい観察がある場合の意味 | 移行関数の出力 |
| --- | --- | --- |
| creating / starting | 起動中 | 再観察待ち（unreachable） |
| idle | 待機 | 同上 |
| busy | 実行中 | 同上 |
| waiting_input | 入力待ち | 同上 |
| unknown / creation_unknown / unavailable / stop_unknown | つながらない | 同上 |
| stopping | 停止中 | 同上 |
| terminated | 終了 | 同上。保存状態だけで終了を証明しない |

| 旧run | 新run |
| --- | --- |
| queued | 送信待ち。送信試行の形跡があれば確認できず |
| sending / send_unknown / awaiting_input / unknown | 終了・確認できず |
| running / waiting_input | 終了・確認できず（移行中の生存を推測しない） |
| completed | acceptance=accepted＋completionEventありなら正常、それ以外は確認できず |
| failed / interrupted | 終了・失敗 / 中断（旧記録由来と明記） |
| superseded | 終了・確認できず。後続との関係を保持 |
| terminated | 未送信取消記録があれば取消、それ以外は確認できず |
| 未知の値 | 確認できず＋移行診断 |
| origin=result（状態とは直交） | phase=result。inboxのresultRunId/deliveryRunIdからresultOfを復元し、二重作成を防ぐ。元結果不明は診断に記録 |

| 旧work | 新しい表現 |
| --- | --- |
| active / completed / failed / interrupted / terminated / cancelled | work状態は廃止。送信列、親子関係、旧JSONを保持 |
| currentRunId / runIds / parentWorkId | 依頼のroot/current参照・同じworkの後続関係・親work最初の送信への参照 |
| finish | rootの申告履歴へ。旧子workのfinishは元JSONに残す（新しいまとめ役申告にはしない） |

| 旧request | 新request |
| --- | --- |
| active / finalizing | 進行中。失敗等・申告矛盾は要確認。次手順も未終了送信もない場合もlegacy-needs-decision |
| completed | 完了（旧確定記録由来）。移行で勝手に再開しない |
| cancelled | 取り下げ |
| 未知の値 / 現行送信不明 | 進行中＋要確認 |

`lifecycle/activityState/connectionState` は最新観察へ統合、`acceptance` は入力照合の
事実、`blocksInput/dispatchConfirmed` は移行判断の補助証拠のみ。`finish.status` は
申告とnative結果の照合へ、`reportPending` は依頼欄の投影へ移す。
`ticket/notification/inbox state` は通知/配送の重複防止履歴として保持し、主状態を
動かす権限には使わない。段階1ではそれらの配送・表示は一切接続しない。

移行は純粋関数 `migrateDirect(unknown)`。入出力の原本を変更せず、二度同じ入力を
渡せば同じ結果を返す。欠落・重複ID・孤立した送信は `issues` に残す。破損入力を
部分的に読めても黙って本番に保存してよいとはしない。段階2で診断確認を必須にする。
旧配列の順序とworkの参照を使うため、並びや親参照が破損しているデータは要手動確認。
初版では合成した旧形式データで検証。追加レビューでは本番ファイルの読み取り専用コピーでも移行・進行検査を行った（後述）。

## 実装・検査方法

- `server/state/common.ts`：判定者、Result、網羅性検査。
- `agent.ts`：観察→状態・送信ボタン、起動/停止/観察の純粋処理。
- `run.ts`：送信と終端、権限、別IDでの手動/限定自動再試行。
- `request.ts`：送信の集約、申告保存、要確認、報告、人間の判断。
- `progress.ts`：進行不変条件、停滞検出、実行可能な次手順。
- `migrate.ts`：旧direct JSONからの純粋な移行と原本保持。
- `tests/state-model.test.js`：許可/拒否、全判定者違反、出口、移行、原本不変。
- `tests/state-types.ts`：禁止された呼び出しの型エラーを検証。
- `tsconfig.state.json`：strict / noEmit / erasableSyntaxOnly、網羅的switch。

Node **22.23.2** の標準型除去で `.ts` を直接importして実行できた。
enum・namespace・parameter propertyは使わず、ビルド手順や起動コマンドは増やさない。
`npm run typecheck` は新規TypeScriptだけを検査する。`npm test` は既存の
`tests/*.test.js` の探索で新テストも実行する。`npm run check` は従来どおり。
旧JavaScript全体のTypeScript移行は行わない。

## 段階2〜4

1. **段階2**：送信の状態処理を接続。観察アダプターでmarker/session/turn/cursor/
   file identity/steerを検証。移行コピーの診断・件数を確認し、停止時間とロールバック、
   排他・保存の原子性・イベント重複排除を設計してからデータ移行する。unknownを終端に。
2. **段階3**：依頼の状態・権限を接続。②の操作は委任・完了申告に絞る。
   acknowledgeを廃止し、要確認の理由と③の判断・再試行・取り下げを画面に用意する。
   通知の一度だけ配送は別の配送台帳で維持。報告正常終了に申告を要求しない。
3. **段階4**：Agentを最新観察から導出し、送信/キュー/補足を整理する。
   依頼側の報告待ちをボタンから除く。Agent向け指示を新しい2操作に合わせて短縮。

## 残る設計事項

- 段階1ではI/O・認証・時計・実際の停止・通知・並列保存を実装しない。①の証拠生成、
  タイムアウト時間、監視切断時の鮮度、重複/順序逆転イベントの扱いは接続前に定義する。
- nativeの遅い成功記録で「確認できず」を自動で正常に変更しない。遅延証拠の監査保存と
  人間への提示はアダプター側で行い、人間が依頼の判断を行う。
- 移行は保守的に実行中も確認できずにする。稼働中移行での二重送信防止・旧プロセス停止、
  旧work列と新しい親子グラフの整合性検査が必要。移行による自動再試行は行わない。
- 今回も設計段階のdraft PR。コピーでの集計は行ったが、本番データの修復は行わない。

## 段階2の接続境界

`run.runModel.state` を保存上の正本とし、`run-lifecycle.mjs` から `state/run.ts`
の生成・遷移・再試行だけを呼ぶ。従来の `run.state` は既存の依頼処理・画面用の
互換表示。`unknown / send_unknown / waiting_input` は一時的な観察ラベルであり、
新モデルの状態ではない。終了した確認不能は `ended/unconfirmed`（互換名terminated）
となり、後から正常終了に書き換えない。段階3・4でこの互換表示を整理する。

追加イベントの判定者: 送信前の宛先消失/境界変化は① `dispatch-blocked`、
補足の予約と未送信取消による所有権復帰は③ `supersede / restore`。
補足の送信開始または失敗で元の追跡を③の判断として閉じる。元の結果を正常と推定しない。
補足がまだqueuedなら元の追跡を復帰できるが、終端になった送信は復帰しない。
現行CLIの独立Agent依頼は `allowAgentRoot` の明示互換オプションで判定者agentを記録する。
既存の子作業retry/resumeは、親のnative受付をactor()で検証済みの場合だけ
legacyAgentRunIdを渡し、判定者agentを記録する。純粋retryは互換指定なしのagent操作を拒否する。
Agent操作の削減・認可の変更は段階3で行い、段階2でhumanと偽装しない。

起動時の `migrateDirect(..., {resumeInFlight:true})` は段階1の保守的な解析とは異なり、
旧sending / awaiting_input / running / waiting_input、およびまだブロック中のunknown /
send_unknownをsentまたはrunningとして保持する。session / turn / input / checkpoint /
fileIdentity / cursor / marker / hash / finishをそのまま引き継ぐ。旧unknown / send_unknownで
blocksInput=falseのものは終端の確認不能にする。再観察でsession変更、未照合での回終了、
照合不能が10分続く場合は①のlostで終了する。正常に照合できる長時間実行は時間切れにしない。
PR #57以前の目印なし送信だけは、既存native入力のハッシュ照合の根拠を遷移に渡す。

段階2ではfinish・acknowledge・work/request状態を維持する。報告も従来どおりfinishが必要。
失敗・中断・確認不能の復旧一覧、削除済みAgentのキャンセル、終了済み報告のreportPending解除
だけを依頼/画面側に追加した。全依頼の進行不変条件への接続は段階3で行う。
