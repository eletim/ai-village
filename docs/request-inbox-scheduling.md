# 依頼入力と秘書の仕事の切り替え

## 契約

状態の正本は依頼グラフ。回答文や回答に書かれたJSONは解析しない。
人間の明示操作、Agent API、実行基盤の構造化された受付・終了記録だけを使う。
依頼を担当することと、現在その依頼を実行していることは別。
秘書は複数の依頼を保持し、実行枠はAgentごとに一つ。工房は未完了の担当依頼を一つに絞る。

新しい依頼は `inputProtocol:1` を保存する。各依頼ノードは `inbox` と `inputClaims` を持つ。
入力は request / supplement / result。入力ID、到着日時、配信した実行ID、対応確定の根拠を保存する。
子結果は requestId/resultId/version への参照を持つ。本文は表示・判断資料だけであり状態の根拠ではない。

- `requests inputs HUMAN_REQUEST_ID WORK_ID` は全文の読取。読取では対応済みにならない。
- `requests respond/finish` は `inputs:[入力ID]` と `results:[結果判断]` を明示する。空配列は暗黙受領しない。
- 今回配信された入力だけを申告できる。別依頼・古い実行の操作は拒否する。
- 申告は同じ実行の正常終了で確定する。失敗・中断・状態不明では確定しない。
- 正常終了だけでは入力を受領扱いにしない。入力未対応の通常成果を子の完成結果として発行しない。
- 新しい補足が届くと、それ以前の申告だけでは依頼を完了できない。子結果への承認後に補足が届く競合も、確定時に再照合する。
- 子結果の受入には `results` も必要。再作業や旧結果の置換は従来の明示契約を維持する。

## 再開と公平性

委任した秘書は初期入力にrespondし、その応答を終える。工房待ちで実行枠を保持しない。
新規依頼・補足・結果は所属先に保存され、次の安全な実行境界で再開する。
一度に最大24入力を割り当て、予約済みの入力群へ後着の入力を混ぜない。
通常は実行予約の作成順。ある依頼への入力が続いても既存の別依頼予約を追い越さない。
補足は同じ依頼でも現在の実行へnative steeringで差し込まず、次の処理区切りで渡す。

入力申告のない正常終了は一度だけ再開し、不足手続きと既存成果を確認させる。
再び未対応なら要確認として残す。失敗・状態不明の実行を自動で送り直さない。
秘書の他の依頼は進められるが、実行基盤自体が不明なAgentには新しい入力を送らない。
工房の未完了依頼は他依頼の割当を保留する。通常待機と要確認は派生状態から表示する。
人間の既存の再開操作は未対応入力を再割当し、明示的な復旧を可能にする。

独立接続の監視は、各監視が終わった時点で進行を反映する。
外部送信待ちは依頼グラフ全体のロックを保持しない。Agent単位の送信排他を維持する。
同じoperationIdの同じAPI操作は保存済みの結果を返す。別内容での再利用は拒否する。
受付不明の外部操作は自動再送しない。

## 人間・Agentの入力先

画面には「新しい依頼」と対象依頼への補足を選ぶ欄を設ける。
Aの待機中にBを実行していてもAを選べる。終了した対象を自動的に新規依頼へ変えない。
人間の補足は `/api/direct/human/requests/supplement`。
Agentは `requests amend {humanRequestId,workId,actorRunId,operationId,instruction}` で直接の子依頼だけに補足できる。
人間の補足には添付・出張資料も保持する。入力の受付と内容への対応は別表示。
送信結果が不明でも保存済みoperationIdから照合でき、再確認は同じ操作IDを使う。

## 導入・復旧

既存依頼は従来の契約のまま継続する。新規依頼から新方式へ切り替える。
既存依頼に新UIから補足した場合は、そのノードに入力管理を付け、新しい補足だけ明示申告を要求する。
過去の対応済み記録を作り直さない。依頼グラフの保存版はv3を維持し、inputProtocolで追加契約を識別する。
未対応のinputProtocolは読込時に拒否する。

反映前にサービスを停止し、direct.json・通知履歴・設定・旧コミットをバックアップする。
反映後は既存依頼/実行IDと履歴の保持、healthのコード版、サービスと画面の読取を確認する。
新方式の依頼を受け付けた後に旧コードだけへ戻してはいけない（旧コードは入力条件を検証しない）。
ロールバック時は受付を止め、新版状態を退避し、反映前のコードと状態を組で戻す必要がある。
その間に行われた外部操作・通知は巻き戻らないため、差分を照合してから復旧する。

## 検証と限界

A待機中にB、B処理中のA補足、遅い接続と正常接続、未申告と有界再開、
補足と完了の競合、子の未申告成果、申告後の子補足、保存・再起動・API再試行を検証する。
ブラウザ検証は専用ポート・使い捨て状態・通知無効の隔離環境だけで行う。

村は入力の対応宣言と対象を検証するが、形式上正しい判断の内容まで保証しない。
取消は既存の明示操作を使用し、外部効果の巻戻しや任意の実行中断は保証しない。
同じファイル/本番環境を別依頼が操作する競合は、worktreeや作業順の管理が別途必要。
再開の資料はサイズを制限した抜粋であり、省略を明示する。全文は読取APIで取得する。

## 補足と報告予約の競合

補足追加は依頼グラフの明示遷移として扱い、報告段階なら元の作業へ戻す。
同じ保存トランザクションで未送信の旧報告予約を取り消す。送信済み報告のnative記録は保持し、Agentの空きを待って補足を処理する。
送信直前の保存境界でも、現在の報告予約・依頼との一致を再確認する。新しい報告の操作キーは元作業IDごとに分ける。
旧版で報告情報だけ消えた予約は、未対応補足と正常終了した元作業の根拠がある場合に再開へ復旧する。

補足は通常の会話ページング・時系列に含め、添付と出張資料も表示する。添付だけの補足も新規依頼と同じ受付条件にする。

## 長い資料と画面履歴

最終報告の資料は質問・補足・最終結果を個別に抜粋してからJSON化し、全体を途中で切らない。
省略フラグと省略補足数、元成果・補足全文の取得先を含める。省略がある場合は報告前に全文を読む。
補足も初期100件の履歴ページに従う。古い補足の本文・添付は追加読込で取得する。
画面の送信照合用には入力ID・操作IDのみを別に保持し、ページ外の本文を毎回転送しない。

## 監視と読取の負荷

接続ごとに一つだけ監視を進め、実行中の監視へ周期ごとの待ち処理を積み増さない。
監視でAgent・所有する実行の状態が変わらなければ永続化を行わない。
監視時の保存失敗からの復元も、対象Agentと所有実行を範囲とする。通常のAPI変更は従来どおり全体の保存境界を使う。
進行処理は同時に一つにまとめ、処理中の新しい変化は再処理の必要として保持する。
完了・取り下げ済み依頼は通常の再評価から除外する。完了時刻・通知予約の初回確定は維持する。
画面用の確定済みデータを保存成功で無効化し、同じ状態の会話取得で全体の投影・コピーを繰り返さない。監視時刻・通信情報は最新値を返す。
保存ファイル形式と送信不明時の再送禁止は維持する。永続化が必要な変更時の全体ファイル書込みは残る。
