# 回答のそばで分かる依頼状態

PR129は会話終了と仕事完了を分離したが、全回答に別欄の確認を要求し、正常完了にも一律「成果確認待ち」を付けた。内部のデータ区分を人間の判断作業にしてしまった。

回答直下に、その回答に関係する依頼のみを表示する。通常相談には仕事欄も確認案内も出さない。関連付けは同じconversationのrequestedBy.actorRunId、delivery.runId、amend/withdrawの保存済みoperation receiptに限る。最新job、許可引用元run、本文類似から推測しない。複数依頼は名称と状態をそれぞれ示す。過去回答の状態も同じ依頼の現在状態を示すが、後から作った別依頼は結合しない。履歴ページにもこのprojectionを保持する。

- 作業中／開始待ち／受付確認中は区別する。
- graphの正常完了は「完了」。秘書への返答が未完なら「作業完了・回答準備中」。返答失敗はその事実を示す。
- 人間が閉じた仕事は「終了」。外部成果の成功を推定しない。
- 停止中は理由と次の動作を同じ場所に置く。
- 正式question資料の具体的な確認事項は、その配送への回答のそばに直接表示する。質問内容から全仕事への承認義務を推定しない。秘書宛て質問は人間の回答待ちと決めつけない。
- 通常の秘書回答に含まれる人間への質問は回答本文で読める。一律の確認待ちバッジは付けない。
- 一覧は補助。秘書自身の停止理由・leader停止理由は異常時だけ残す。

変更は読取projectionと表示のみ。graph保存、受付照合、送信排他、旧unknown、完了・成果採用の内部区分を変更しない。質問資料は履歴として残し「未回答」と断定しない。

検証: actor/結果配送/訂正の厳密な関連付け、別会話・無関連相談・後続仕事の非混同。実サービスfixtureの会話→複数job→finish→結果返答、question配送、受付不明を1440px/390pxで表示。通常相談に確認要求なし、完了の明示、異常時も秘書送信可能、履歴ページの保持を確認。
