# 会話表示・起動・送信状態の修正（2026-11-04）

URL: http://100.87.176.23:5173/agents （VPN内）

## 原因と変更

起動APIそのものは両工房の0 Agent状態で動作することを確認した。入口が「起動・工房設定」の中にあり、表示中の工房を引き継がないため、工房を選んでその場所に起動する操作が分かりにくかった。常時表示する「＋ Agentを起動」と空の場所の起動ボタンを追加し、工房・村長の家の選択を引き継ぐ。起動の同一requestIdを並行処理しても同じAgentを返すよう直列化した。明確に拒否された入力を修正しても古いrequestIdが残る問題も修正した。起動途中の通信結果不明では同じIDを保持し、重複起動を防ぐ。

送信不能には以下のコード上の原因があった。

- UIは `state === idle` と全実行履歴から判断し、バックエンドは別の条件と保存済みAgent状態で判断していた。待機へ復旧した実機に対しても古い状態で拒否し得た。
- 結果不明の実行は最新のランタイムが終了しても永久に送信をブロックしていた。
- 再起動直後の状態が再確認前に表示され、UIの定期更新と操作後の更新にも競合があった。
- 送信応答が失われた時の受付ID・下書きが再読み込みで消え、送信中に書き足した文章もフォームresetで消える可能性があった。

## 状態と送信可否

| 項目 | 意味 |
| --- | --- |
| `lifecycle` | Agent／端末の稼働可否。alive、starting、unavailable、unknown、stopping、terminated |
| `connectionState` | 接続確認済み／接続不明 |
| `activityState` | ランタイムのidle、busy、waiting_input、unknown |
| run `state` | 指示ごとのsending、running、completed、failed、interrupted、unknown等 |
| run `blocksInput` | その実行が次の入力受付を妨げるか。結果の成功／失敗とは別 |
| `canSend` / `sendReason` | 上記からバックエンドが計算する送信可否と理由 |

UIはcanSendを使う。送信APIもAgent単位のロック内でPurpleMuxとネイティブ記録を再取得し、同じ判定を使う。画面だけを強制的に有効化しない。

正常完了・ランタイム失敗・中断は対応するnative turnのイベントで確定し、実機が待機中なら次の指示を許可する。外部入力で実行中・入力待ちなら許可しない。接続断はunknownでありterminatedではない。バックエンド再起動直後もcanSendをfalseにして、監視の再確認後に開く。

結果不明の実行は成功へ書き換えない。同じランタイムの送信前チェックポイントより後の入力が終了境界に到達し、実機の待機も確認できた場合、過去の結果不明を保持したままblocksInputだけを解除できる。何も入力が観測されず、受付成否も不明の場合はブロックを維持する。これは安全上、待機表示だけで推測して解除しない。

送信意図は副作用より前に永続化する。自動再送なし。同じrequestIdへの問い合わせ・再受付は保存済み実行を返す。ブラウザは送信応答を失った場合にも下書き・受付IDをsessionStorageへ保持し、通常送信を保留する。「送信結果を確認」を人間が選んだ場合のみ、同じID・同じ内容で確認する。元の受付がなければ最初の一度として受け付け、すでに受け付けていれば再送しない。

## 会話

自分の発言は右、Agentの出力は左。時刻は小さく表示。出力本文は省略せず、native transcriptのcommentaryと最終応答も内容として保持する。指示の状態、エラー、通知状態も会話内に表示する。

Agent別の独立スクロール、下書き、閲覧位置を維持。タブ切替、絞り込み、定期更新、同一ブラウザタブの再読み込みで復元する。送信中に追記した文章は消さない。終了確認済みAgentだけを通常表示から除き、履歴は残す。全部／工房／特定Agent、可変拠点数、最大9分割と次ページ、秘書も維持する。

## 出力形式への依存の調査

直接操作・旧秘書・旧工房bridge・旧承認経路を再調査。実行マーカー、モデル生成JSONの行動選択、出力スキーマによる制御は使っていない。今回、旧経路に残っていた「本文が空なら未完了／承認不可／復旧不可」という条件も除去した。報告はホスト側のphase、生成完了時刻、保存済み報告フィールドの存在で管理する。空本文の復旧・承認テストを追加した。

PurpleMuxのstatus API、状態遷移、Codex parserも確認。session ID、native input／turn ID、終了・中断イベントを利用する既存方式を維持し、AIの本文に識別子を要求しない。PurpleMuxのリポジトリ変更は不要だった。曖昧な帰属は不明のまま、達成状況も未判定のままにする。

## 検証

自動テスト90件成功。ブラウザテスト28件成功・既存条件付き1件skip。新しいテストは3種類の終端からの送信復帰、接続復旧、再起動、結果不明の入力受付解放、同一ID起動の並行要求、0件からの起動入口、左右表示、再読み込みでの下書き／スクロール復元、送信応答消失後の同一ID確認、空の旧報告の承認・復旧を含む。

実機は専用の状態ディレクトリとlocalhost:5186で同じコードを起動し、E-ryzenはローカル、E-frontierはSSHで操作。検証結果・スクリーンショットは `.runtime/validation/state-*`（Git対象外）。通常サービスの通知設定・トークンは変更せず、検証用バックエンドの通知は無効化した。


実機で確認した内容:

- 両工房が0 Agentの状態からブラウザの新しい入口でCodexを起動。指示→返答→追加指示を並行実行。
- 左右の吹き出しと小さい時刻を確認し、両Agentの下書き・スクロール位置が再読み込み後も残ることを確認。
- CLI境界で通信失敗を注入。接続不明・送信不可になり、バックエンド停止／再起動後に元のturnの完了を取得し、次の指示を受付。物理回線の切断試験ではない。
- 送信途中の失敗で受付確認が得られなかった指示も発生。これを完了扱い・自動再送せず保持。別の明示的なPurpleMux入力がnative terminal境界に到達した後、新しい指示の受付が復旧することを確認。
- 両PCの専用Codexをsleep中にinterrupt。両方ともinterruptedを記録し、その後の新しい指示を正常受付・完了。
- PurpleMux CLIから直接入力し、続くAI村からの指示が別turnとして完了。制御用マーカーは一切要求していない。
- ×で両Agentを終了し非表示を確認後、同じ工房で新しいAgentを再起動。通常運用データの登録内容・既存Agentは変更していない。
- Claudeも両PCに専用Agentを起動。認証期限切れのauthentication_failedをfailedとして保存し、canSendがtrueに戻って次の指示を受付することを2回確認。認証を変更していないため、Claudeの正常応答は未検証。
- 検証用の計6 Agentを対象IDで終了。空になった検証用workspaceだけを削除し、無関係な既存タブが残っていることを照合。

残る制約: Claudeの正常応答にはログイン更新が必要。通知の実配送は今回の検証範囲外。ネイティブ記録が欠損し受付／実行状態を特定できない場合は、送信を無理に許可せず不明として残す。
