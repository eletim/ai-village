# 画面ごとの必要分取得（lean fetch）

画面ごとに、その場で表示に要るデータだけを取得するようにする。圧縮（gzip）の追加は人間の判断で対象外。既存のワークスペース同期は、もともとgzipに対応している。

## 計測（2026-11-25、本番村、非圧縮）

| 経路 | 使う画面 | 1回の量 | 取得の頻度 |
|---|---|---|---|
| `GET /api/direct` | 村の地図（`/`） | 34.6MB | 開いた時と、村に変化があるたび（SSE通知ごと）に全体を取り直す |
| `GET /api/direct?view=workspace`（focus指定なし） | 画面からは未使用（旧API利用者向け） | 13.4MB | ― |
| `?view=workspace&sync=1&focus=[]` | ワークスペースの初回（概要だけ） | 0.55MB | 開いた時に1回 |
| 同上で表示中のAgentに絞った差分 | ワークスペースの初回（表示中カードの会話） | 0.6〜3.4MB（会話の量による） | 開いた時に1回。以後は変化分だけ |

全データ34.6MBの内訳は、Agentの記録（nativeTurns）15.3MB、実行（runs）11.2MB、依頼（requests）7.4MBで、ほとんどが過去の本文と依頼グラフ。地図はこれを使わない。

## 画面ごとに使うデータ

| 画面 | 初期取得（いま表示に要るもの） | 遅延取得（開いた・スクロールした時） |
|---|---|---|
| 村の地図 | Agentの登録（名前・場所・Project・状態・接続）、工房、Project、要確認／未確認の印、各Agentの色を決める最新の実行1〜数件の状態 | なし（会話はワークスペースで見る） |
| ワークスペースの一覧・カード | 全Agentの概要（状態・印・リーダー表示・Project）、進行中の依頼の制御情報 | 表示中カードの会話（focus）。他のProjectや終了Agentの会話は取らない（既存） |
| 会話 | 表示中Agentの直近100件と、未完了の操作 | 「古い会話を読み込む」で100件ずつ（既存） |
| プロフィール | Agentの概要に含まれる `conversationWork`／`conversationControl`、Project方針（開いた時に取得：既存） | ― |
| 終了Agentの履歴ダイアログ | 選んだAgentの会話（開いた時にfocusへ追加：既存） | 古い分は同上 |
| 依頼の操作（完了・再試行など） | 一覧に要る要約だけ | 操作の直前に `requests/get` で全文（既存） |

## 段階1：表示を変えない切替（今回実装）

1. **地図専用の取得 `GET /api/direct?view=map`**（`server/map-view.mjs`）
   - 送るもの：
     - 削除されていないAgentの、地図に要る項目
     - 工房とProject
     - レビュー印（未確認・要確認のみ）
     - 各Agentの色を決める最新の項目だけ（全体の最新、観測中セッションの最新、失敗判定用の最新nativeTurnと、それらに対応する実行）
   - 本文・依頼グラフ・履歴は送らない。
   - `villageModel()` が完全版と同じ結果になることを確認済み（後述のテスト）。
   - 本番データで 34.6MB → 約24KB。
2. **ワークスペースのAgent概要から、画面が使わない監査用データを除く**（`workspaceSnapshot(..., {lean:true})`）
   - `secretaryHandover` は画面で未使用なので送らない。
   - `runtimeMigrations` は、画面が読む最後の1件の `legacyRetirement` だけを送る。
   - 本番データで、初回の概要が約0.55MB → 約0.29MB。

同期の仕組み（`sync=1`、差分・カーソル・focus・ranges）、変更通知（SSE）、presence、通知、正式API（`requests get` など）は変更していない。完全版の `GET /api/direct` もそのまま残している。

## 戻し方

- サービスを `VILLAGE_LEGACY_FETCH=1` で再起動すると、次の2つが元に戻る。
  - `?view=map` は完全版を返す（地図はどちらの形も読める）。
  - ワークスペースの概要も完全版に戻る。
- コードを戻す場合は、統合ブランチで該当PRを revert する。データ形式の移行はしていないので、データの戻しは不要。

## 段階2：折りたたまれたやり取りの本文を、開いた時に読み込む（V2、人間了承済み）

ワークスペースの会話で、折りたたみ表示になる部分の本文は、同期では送らない。対象は次の2つ。
- Agent同士の依頼・補足の入力（プログラム／Agent由来の補足通知を含む）
- 人間向けに公開されていない出力（途中経過、成果提出、作業の元回答など）

折りたたみを開いた時に `GET /api/direct/agents/:id/entry-body?entry=…&side=input|output` で本文を取得する。取得中は「読み込み中…」と表示する（人間了承済み）。

- **判定：** 折りたたむかどうかは、画面と同じ関数（`isHumanInput`・`isVisibleAnswer`・最終報告の判定）でサーバーが決める。そのため、画面がそのまま見せる本文（人間の発言、秘書の回答、最終報告）は、従来どおり同期に含まれる。
- **実行中の出力：** 実行中のものは折りたたまれていても同期で送り続け、途中経過の流れ方を変えない。終了したものだけを後から読み込む。
- **本文の更新：** 本文ごとに版 `v` を付ける。本文が変わると版が変わり、開いている折りたたみは自動で取り直す。閉じている折りたたみは、何も取得しない。
- **失敗時：** 「本文を読み込めませんでした。閉じて開き直すと再試行します。」と表示する。自動では再試行せず、人が開き直した時だけ再試行する（再描画で開き直された折りたたみからは再試行しない）。
- **古い会話：** 「古い会話を読み込む」で取得するページにも同じ規則を当てる。
- **戻し方：** `VILLAGE_LEGACY_FETCH=1` で、本文も同期に含める従来の形に戻る。

V1（会話の初期件数を減らす）は、人間の判断で実施しない。

## テスト

- `tests/lean-fetch.test.js`
  - 乱数で作った300通りの村で、地図の結果が完全版と一致し、本文を含まないこと。
  - 地図用データは、各Agentの最新の数件だけを持つこと。
  - lean版のワークスペースは、上記の2項目だけが完全版と違うこと。
- `tests/lean-fetch-http.test.js`
  - 実サーバーで、地図用データが完全版の1/50未満であること。
  - `VILLAGE_LEGACY_FETCH=1` で元の量に戻ること。
- `tests/lean-fetch.test.js`（段階2）
  - 折りたたまれる本文だけが同期から外れること（人間の発言・公開回答・最終報告・実行中の出力は残ること）。
  - entry-body が外した本文をそのまま返すこと。本文が変わると版が変わること。
  - 補足通知の扱い。
- `tests/browser/lazy-bodies.spec.js`
  - PC幅・スマホ幅で、開くまで取得しないこと。開くと「読み込み中…」の後に本文が出ること。
  - 同期を挟んでも再取得しないこと。本文が変わると取り直すこと。
  - 失敗の表示と、開き直しでの再試行。
- `tests/browser/lean-fetch.spec.js`
  - 地図（PC幅・スマホ幅）が `?view=map` だけを取得し、横はみ出しがないこと。
  - ワークスペースが、従来の同期で表示されること。
