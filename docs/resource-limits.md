# アップロードとコマンドの資源制限

## 新規アップロード

| 資源 | 上限 | 理由・動作 |
| --- | --- | --- |
| 1ファイルの受信量 | 40 MiB | 約33 MiBの既存PNG保存・転送テストを維持。スマホスクショ（1220×2712、約0.5 MB）にも余裕を持つ |
| 画像の画素数 | 制限なし | 画素数では拒否せず、自動縮小もしない。Sharpの暗黙の画素上限も無効化 |
| 受信から保存まで | 全経路合計4件／サーバープロセス | 添付4件の仕様を維持しつつ、無制限の本文蓄積を避ける。待ち行列を作らず503 |
| 画像デコード・変換・保存 | 全ImageStore合計2件／プロセス | メインのimagesとAttachmentStore内のimagesで共通。待ち行列を作らず503 |
| 受信期限 | 120秒 | 遅い通信にも余地を持たせ、未完の受信による枠の永久占有を避ける。408 |

Content-Lengthの超過は本文を読む前に拒否する。宣言なしのchunkedも各チャンクの合計を検査し、超過チャンクを蓄積せず受信をpauseする。413のJSONエラーを返して接続を閉じ、残り本文をdrainしない。保存層でもサイズを再検査する。Sharpは入力と保存後の寸法確認の両方で `limitInputPixels:false` を指定し、単一ページのPNG/JPEG/WebPだけをPNGへ変換する。

ブラウザのファイル選択・ペーストとCLIは共通の40 MiB定義で事前検査する。復元済み下書きなどを含む最終判定はサーバー。413/503の理由は既存の送信失敗表示へ返し、下書きを保持する。添付件数は引き続き4件。

### 経路の洗い出し

- Agent画面の画像・ファイル・ペースト: POST /api/attachments → AttachmentStore。画像は共通ImageStore。
- 画像報告・images upload: 呼出元CLI → POST /api/images → ImageStore。/api/villageのimages uploadはサーバーパスを受け付けない。
- 出張: PC／cwd／notesの構造化データ。独立したファイル受信経路はなく、付随ファイルは同じ添付経路。既存notes等の長さ制限は維持。
- 添付選択／Agentへの転送: 保存済みIDを使用。新規アップロードは上記制限を必ず通る。
- 既存の保存画像・ファイルの読取／転送には今回の上限を遡及適用しない。

本文の保持は受信枠数×40 MiBで頭打ち（連結時の一時コピーは別途必要）。変換枠は設けるが、libvips／圧縮処理／キャッシュを含むRSSの厳密なバイト上限ではない。変換後PNGは受信時より大きくなり得る。総保存容量、OSの接続数、利用者別レート制限、複数サーバープロセス間の制限、変換CPU時間のハードリミットは対象外。

## コマンド終了

POSIXでrun()が起動する短期コマンドには、signal指定の有無を問わず専用プロセスグループを作る。タイムアウト・明示キャンセル・出力上限超過では同じ終了処理を使い、そのグループへSIGKILLを送る。通常はcloseで完了し、パイプが閉じない場合も250 ms後にローカルパイプを破棄して呼出元を返す。setEncodingによるUTF-8分割処理を維持し、超過後のstdout追加も止める。

既存PurpleMuxサーバー／tmux／Agentのグループ、他のコマンドのグループには信号を送らない。Agentの終了は従来どおりprocesses.mjsのPID・開始時刻等の所有照合を使用する。新たに起動するCLIが同じグループに子を残せばその子も終了対象となるため、長寿命サービスの起動自体をrun()で扱う場合は独立セッションへ分離する必要がある。

ローカルSSHプロセスの終了はリモート副作用の取消保証ではない。遠隔プロセスやsetsidで脱離した子孫、カーネル内の割込不能待機はプロセスグループだけで強制回収できない。自動再送は追加しない。Windowsでは直接の子への終了にフォールバックし、子孫回収の保証はPOSIXを対象とする。

## 検証

単体は受信中断（宣言なしを含む）、48MP画像の寸法保持、共有変換枠、HTTPの5件目拒否、正当なスクショ、タイムアウト／キャンセル／出力超過時の子孫終了、別グループの存続、UTF-8分割を検査する。子孫は/procで実行が残らないことを確認（終了直後のzombieの回収時期はOS依存）。隔離した実サーバーでは画像・添付両APIの正常／超過、既存大画像の転送、CLIを検証する。ブラウザは実アップロードと超過エラー表示を検証し、Agentへの依頼POSTだけをテストダブルとする。本番Agentへの送信はしない。

検証結果（基準21fea67）: npm testは348成功・1スキップ（追加10件）、基準は338成功・1スキップ。初回の全体実行ではrequests-httpの件数アサーションが一度2対3で失敗したが、関連テストおよび全体の再実行は成功。タイミング依存の可能性があり、既存不具合とは断定しない。構文・型・ビルド成功。Playwrightは修正後126成功・15失敗、基準125成功・15失敗で、失敗した15件の集合は一致。元の再現例（sleep 2 & wait、timeout 50 ms）は53 msで戻った。ポート5397〜5399と使い捨て状態のみを使用し、通知オフ。本番を変更・再起動していない。

画素制限撤廃の回帰テストでは8000×6000のPNGを実行時に生成し、画像・添付両APIで201、保存寸法、取得した画像の一致を確認する。ブラウザでも48MP画像を添付・取得する。巨大fixtureは保存しない。画像の展開・処理に必要なメモリは画素数に応じて増えるため、利用可能なメモリやデコーダ固有の形式上の限界によって処理が失敗する可能性はある。
