# 依頼元Agentによる同じ担当への継続指示

## 目的と既存機能との差

秘書は依頼の目的、残された成果、実施済み操作を確認して次の仕事を選ぶ。プログラムが中断理由の文章から再実行を決めることはしない。

既存の結果配送は失敗・中断も親へ返せる。結果の採用は `respond/finish`、別担当へのやり直しは `rework` と `delegate(replacesRequestId)` で足りる。未開始の担当選択は `assignPlan`、実行中の追加要件は `amend`、人間による復旧・担当変更は既存の人間専用APIを使う。

不足は、終了済みの子を同じ担当・作業場所で継続する入口が人間専用の `resume/retry` しかなかった点。今回 `continueChild` だけをAgent仕様・CLI・HTTPへ追加する。人間専用APIを開放せず、依頼・runの既存モデル、キュー、結果配送を再利用する。担当変更、親自身の自動復旧、監督Agent、新しい復旧状態機械は追加しない。

## 操作契約

正式なフィールド・説明の正本は `server/agent-rules.mjs` の `agentActions.continueChild`。`rules get work` と CLI `help` から取得する。

```text
requests continueChild JSON {
  humanRequestId, workId, actorRunId, targetRunId,
  revision, operationId, instruction
}
```

HTTPは `POST /api/direct/requests/continueChild`。`workId` は直接の子、`actorRunId` はその親依頼の現在実行中のrun。`targetRunId` は子の現在run、`revision` は `requests get` で読んだ依頼全体のrevision。`agentId` による担当変更は拒否する。場所の表示名や「秘書」という名前を権限の根拠にしない。

実行前に `requests get/results/inputs` と必要な登録情報を読み、目的、未対応の追記、途中成果、作業場所、外部操作の成否を確認する。確認した事実と未完了部分を `instruction` に記し、実施済み作業の繰り返しを指示しない。別担当が必要なら既存の差し戻し・再委任を選ぶ。

- 親は受付照合済みの現在runで、同じ依頼の直接の親であること。root自身、祖先から孫への操作、別依頼・古いrun・報告runからの操作は拒否。
- 子は非終端の依頼で、その最新runに native の正常終了・失敗・中断の確定記録があること。送信中、実行中、終了不明、追跡打切り、Agent停止は継続根拠にならない。
- 現在のnative記録も同じsession・turn・入力・ファイルを示し、終了位置以後に入力がなくidleであること。受付時と実際の送信前に再確認する。送信前に境界が変われば未送信で止める。既存ランタイムの再起動や強制停止はしない。
- 最新結果への確定採否、現在runの未確定accept/rework、未解決の置換予約とは併用しない。結果を読んだだけなら継続可能。失敗した親の未確定申告だけでは将来の有効な親runを永久に妨げない。ただし既に別の再依頼が作られている事実は失敗で消えないので、その依頼が残る間は元依頼の並行再実行を拒否する。
- 同じoperationId・同じpayloadの再送は同じ新runを返す。revision競合や別payloadの使い回しは拒否。応答喪失時に別IDで送り直さない。親runが交代して再試行を拒否された場合は、`requests get` のrunにある `childContinuation.operationId` を確認して受付済み操作を追跡する。

継続は既存の `attempt` として即時保存し、同じNode/assigneeに新しいwork runを追加する。`retryOf`、`parentRunId`、operationId、指示主体（agent）を記録する。旧runの出力・申告・結果版は残り、新runの結果に混ぜない。未確定の旧申告の失効、古い結果入力の退役、新しい結果の配送は共通モデルの既存処理を使う。人間由来の訂正には分類しない。添付・出張資料の参照とAgentの作業場所/sessionを保持する。

`delegate` と同様、継続の受付は親の正常終了を待たず予約される。採否の申告は従来通り正常終了で確定する。この二つを混同しない。親は継続後に自分の入力へ `respond` し応答を終え、子の結果配送による再開を待つ。継続した古い結果をaccept/reworkする必要はなく、新しい結果を確認して採否を明示する。

## 検証と限界

機械テストは `tests/child-continuation.test.js` と `tests/child-continuation-http.test.js`。隔離状態・native記録fixtureで、直接親子/孫/別依頼、確定した中断/失敗/正常終了、稼働中/不明/境界変化、未確定採否、置換、競合、同一操作再試行、保存失敗、再起動、遅延旧成果、文脈保持、結果配送から秘書再開を検証する。HTTPテストは空きポート・使い捨て状態・偽native記録・偽通知コマンドのみ使用し、実AI検証とは区別する。

村内での同一操作の二重予約を防ぐ仕組みであり、外部サービスへの副作用がexactly-onceであるとは保証しない。runが終了していても外部操作の成否確認は依頼元の仕事。実行環境が失われた場合や受付不明の場合に、都合よく「終了済み」と書き換えて再送しない。

保存形式の移行や既存Agentの作り直しは不要。可変work仕様のrevisionだけが変わり、固定bootstrapとreport仕様は変わらない。新規則を取得しない旧セッションへ自動で新機能習得済みとみなさない。導入後に継続予約を受け付けた状態で旧コードへ戻すと送信直前の追加境界検査がなくなるため、未送信予約を放置した単純ロールバックはしない。受付済みの操作と外部効果を照合してから運用側で判断する。

## 親による隔離実機受入手順

1. 本番と異なる専用ポート・状態ディレクトリで検証村を起動。healthのrevisionと状態ディレクトリ、ブラウザ/CLIの接続先を確認し、通知は無効化する。テスト専用Project、空の作業場所に新規秘書と工房を用意する。本番Agent・既存仕事は使わない。
2. 秘書に「専用フォルダで段階的にファイルを作り検証する。工房が中断したら結果・作業記録を確認し、適切な方法を自分で選んで目的まで進め、成果をレビューする」と依頼する。秘書に `rules get work` を読ませ、通常の正式delegateで工房へ依頼させる。工房には各段階で進捗をローカルファイルに残させ、外部サービスへの操作は禁止する。
3. 工房の受付が `running` になり部分成果ができたことを確認。検証担当者がそのテスト工房のnative turnだけを中断する。村のAgent停止（プロセス破棄）とは区別する。中断したturn/session、受付input、終了イベント/位置、idleを記録する。これらを取得できない場合は未検証/拒否として記録し、状態を直書きしない。
4. 親が応答を終えた後、子の中断結果配送により親が再開することを確認。人間から追加のresume命令を送らず、親がget/results/inputsで状況を読み、同担当継続を選べば `continueChild` を呼ぶことを観察する。元workId/Agent/workspace/sessionが同じ、新runのretryOfが中断run、指示主体agent、操作IDが一つであることを記録。別担当を選んだ場合は既存rework/delegateの判断理由を記録し、同担当機能の試験成功と混同しない。
5. 親はrespondして終了。工房が部分成果を読み、完了済み段階を繰り返さず残りを進めることを確認。結果配送で親が再開し、成果を全文確認してaccept/reworkする。最終報告はrootで一度、子・途中報告では完了通知されないことを確認する。
6. 比較試験では中断確認前や受付不明の時点で継続を試み、拒否と送信なしを確認する。HTTP応答を受け取れなかった想定で同一payloadを再試行し、新run/送信数が増えないことも確認する。失敗と人間の介入があれば省略せず記録する。
7. 親子run ID、operationId、revision、nativeイベント、部分成果/最終成果、親の判断と採否、通知件数を隔離環境の証拠へ保存する。検証後はこの専用環境だけ整理する。工房による実装提出は実機受入の完了を意味しない。
