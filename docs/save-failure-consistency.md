# direct.json の保存失敗と実行境界

変更の正本は引き続き状態モデル。外部操作を実行できるのは、その意図を direct.json に保存できた場合だけとする。

## 保存境界

`DirectAgents.persist()` はモデル変更と保存を短い排他区間にまとめる。他の監視やAPIが同じメモリを別の保存へ混ぜることを防ぐ。SSH・PurpleMux・ネイティブ記録の読取は外で行い、取得した事実を境界内で反映する。外部送信も境界の外で、意図の保存成功後に行う。既存のAgent別・依頼グラフ・Projectのロックは維持する。

保存が失敗したら、変更前のオブジェクトを同じ参照のまま復元する。run/work/Agentへの参照を保持する呼出元にも復元が届く。境界内で一度保存に成功した場合、その時点を次の復元地点にする。後続の失敗で、すでに保存した意図まで取り消さない。

| 経路 | 保存失敗時の扱い |
| --- | --- |
| 新しい依頼・delegate・steering | 受付保存の失敗は追加・関連付け・元runの変更を復元。同じIDで再試行できる |
| 受付保存後の送信準備・送信結果保存 | 受付済みの待機／送信状態を返す。受付自体が失敗したとは返さない。送信意図の保存前は送らず、送信意図の保存後は再送しない |
| finish | 申告とrevisionを復元。申告保存後のsettle失敗では保存済み申告を保持。同じoperationIdは重複登録しない |
| result配送・report作成・限定自動復旧 | 新しいrunと参照・試行予算を一緒に保存。失敗中は送らない。復旧後のpumpで保存してから1回だけ送る |
| 人間の完了扱い・取り下げ・未送信取消・手動再試行 | 判定・revision・runの変更を復元。未保存の完了通知や取消を適用しない |
| Agent作成・停止 | 起動／停止意図を外部操作前に保存。応答後の保存失敗では保存済み意図を保持。起動結果不明を自動再作成しない。停止の再試行はtab・所有プロセスを再照合 |
| Project削除 | 各段階の意図・進捗を保存。最終保存失敗では直前のrunningに戻し、deletedの冪等成功を返さない |
| 監視・Agent/Project/工房メタデータ・既読・報告設定・入力封筒 | 同じ境界を使用。保存失敗を接続エラーに変換しない |

人間の完了扱い／取り下げは既存のrevision検査を維持する。operationIdを持たない操作に新しい冪等APIは導入しない。

## 通知

依頼の通知を `pending → attempting` に保存してから通知実装を呼ぶ。この保存の失敗は pending に復元し、後の監視で安全に再試行できる。保存待ち中に依頼完了が巻き戻る場合もあるため、排他区間に入ってから完了とpendingを再確認する。

通知実装を呼んだ後の失敗は `delivery_unknown` とする。それも保存できなければ、保存済み attempting を残す。再起動時も再送しない。通知結果を読み取れなかった場合に「必ず届いた」とは判断しない。

## 置換後の失敗・限界

一時ファイルの書込／fsync／rename前の失敗は復元できる。rename後のディレクトリ同期が失敗した場合はディスクの結果が曖昧なので、メモリを古い状態に戻して処理を続けず、そのプロセスの以降の保存境界を拒否する。ストレージを確認し、direct.jsonを確認したうえで再起動する必要がある。

外部操作とローカル保存を単一トランザクションにはできない。意図保存後・実送信前のプロセス終了や、外部送信後の結果不明では、自動再送しない既存方針を優先する。厳密なexactly-once配送は保証しない。通知実装内部のジャーナルやCLIの不明結果も従来の保守的な扱いを維持する。

チェックポイントは状態全体のオブジェクト数に比例する時間・メモリを使う。今回の排他はモデル変更とローカル保存だけであり、ネットワーク読取は並行のまま。大規模履歴での負荷試験、マルチプロセスによる同一状態ディレクトリへの同時書込は対象外。

## 検証方式

一時ディレクトリの実DirectAgents／DirectStoreを使い、書込失敗を各境界に注入。renameの実失敗、並行保存への混入、通知の並行claim、再起動後の重複抑止も検査する。外部Agent／通知は記録するテストダブルを使い、送信回数と保存内容を検証する。本番データ・本番Agent・通知先は使用しない。

今回の検証結果: 基準 2a15d67 は npm test 322成功・1スキップ、修正後は338成功・1スキップ（追加16件、失敗0）。構文・型・ビルド成功。通知オフの隔離ポート5398/5399でPlaywrightを実行し、両方125成功・15失敗、失敗ケースの集合も一致。基準比較の最初の実行はvendor資材の配置不足で無効とし、資材を揃えて再実行した。実Agent／実通知の送信は行わず、保存失敗の決定的な再現を優先した。
