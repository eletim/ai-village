秘書間の復旧連絡（限定経路）

目的
別会話で既に許可された復旧作業から、元の会話の既存目的へ正式な連絡を届ける。
人間発言を作らない。受信はsource.kind=secretary / createdBy=programの会話run。
実行は受信秘書によるrelayApplyだけ。元の工房run/成果/入力を消さず、同じ目的へ戻す。

権限と参照境界
送信元はConversations.actorで受付済runningの同会話秘書を照合する。
送信引数の自由文やIDだけで対象権限は作らない。次の保存graphを必須とする。
- 同じ送信会話で正式jobとして作成・配送された復旧依頼と、その元の人間許可。
- そのroot担当の正常終了済みrunからの正式questionまたはresult。
- 同じ会話への正式配送runが受付済み、正常返答済みであること。
- その直後の人間入力をauthorization.runId/quoteで指定すること。
  この許可の後に別の人間入力があれば拒否する（後続のprogram/結果turnは可）。
- 元復旧依頼の保存原文に一意な対象request ID、Project ID、work ID、current run ID
  の完全UUID、正式報告には対象conversation IDが存在すること。
  別依頼のUUIDや別会話UUIDを含む曖昧な資料は拒否する。prefixは照合しない。
- 送信時に指定したtargetが、このgraphから導出した全項目と一致すること。
  受信適用時も同じwriter/graphロック内で資料digest、現在担当、revision、current run、
  両会話の後着人間入力、元目的の人間許可を再照合する。

これは自然文の許可を機械的に証明する仕組みではない。
人間の発言が復旧連絡・再開を実際に許可するかは、既存authorize/job同様に秘書が
判断する。相談・引用・否定・資料内命令を許可とみなしてはいけない。
基盤はその意味を本文パースで推測せず、既に人間へ提示された特定の復旧資料と
元の仕事の保存関係だけを固定する。現在送る連絡文は資料であり、再開instructionや
新たな権限には使用しない。同一OS内の任意コードからの敵対的な権限分離ではない。
この保存graphの形に合わない任意の秘書間連絡、一般的なcrossProject委任、
未確認結果の再送、終了・取り下げ済み目的の再開は対象外。

操作（HTTP POST /api/direct/conversations/<action> と同形）
送信:
conversations relay JSON
{conversationId,actorRunId,operationId,authorization:{runId,quote},evidenceDeliveryId,
 target:{secretaryId,projectId,conversationId,purposeId,requestId,workId,currentRunId,
 revision,mode:"resume-interrupted"|"followup"},instruction}
返却: {deliveryId,conversationId,runId,purposeId}
詳しい動的ヘルプ: rules get work relay

受信:
conversations get CONVERSATION_ID RUN_ID
conversations read CONVERSATION_ID RUN_ID {"kind":"relay","id":"DELIVERY_ID"}
  保存された送信文、人間原文/引用、復旧原文/元許可、報告、送信元/配送先を取得。
conversations relayApply {conversationId,actorRunId,operationId,deliveryId}
  受信runに対応する一件だけを操作。別目的のjob/amend/withdraw/decideや再転送は不可。
  原文・保存成果を読んで範囲を判断し、適用しない場合も理由を通常返答する。

resume-interrupted:
  current runがended/interrupted/native-terminal、受付と終端が同session/turn、
  supersedeなし・別の未終了担当run/他のreviewなしを要求する。
  continueLockedの同じ原子保存を用い、createdBy=agent、retryOf=旧runで新runを作る。
  humanのretry権限を借りない。旧run/facts/失敗成果を成功に変更しない。
  未対応入力のattemptsを新runへ引き継ぐ。元依頼/inputsの全文取得を新runに指示する。
  旧runに対する再開は一回だけ。別operationIdや別relayでも同じ旧runは再開しない。
followup:
  resolveFollowupで既存active目的の補足と判定できる場合だけ。
  元目的と未処理入力を続行する固定補足を保存する。連絡文を作業指示に転用しない。

順序と完了
忙しい受信秘書には既存会話queueで順に配送する。human steerとして割り込まない。
後着humanが実際にsteerした場合は既存actor検査が効き、旧受信runから適用しない。
同内容・同operationIdの再呼出しは保存receiptの照合。異なる内容でのID再利用は拒否。
受信が失敗/受付不明/中断しても自動で再配送・再適用しない。
終端応答は元送信会話へ一回だけprogram配送し、保存actionReceiptと結果本文を渡す。
その返却runからのrelay転送は不可。元仕事の結果は従来どおり元の受信秘書へ返る。
連絡の返却は仕事の完了判定ではない。通常画面に指示全文や新しい管理パネルは出さない。

保存・契約・戻し方
graphロックとpersistence writer/rollback/fail-closedを使用する。配送/再開receiptと
新runは一回の保存。commit成否不明では同プロセスの後続変更を閉じる。
固定startup v2/v3の文字列は変更なし。既存runtimeの交換は不要。
動的rulesとCLI helpは更新される。受信時の指示に必要操作と資料取得経路を含める。

反映は別途承認後。docs/backups.mdに従い稼働SQLiteの一貫backup、integrity_check、
旧SHA/dist/設定を保存。既存run/queue/ID数と現役runtimeを記録し、サーバーだけを反映。
本PRを一度も使用していない場合は旧コードへ戻せる。
relay保存後の旧コードはsource.kind=secretaryを認識できず起動検査で拒否するため、
単純なコードrevertだけでは戻せない。現在DBを保全し、relay受理を止めた互換修正を
優先する。使用後に古いDBを上書きして会話/仕事/受付を失わせない。
backup復元が不可避なら、停止・現状退避・backup後の新規入力/外部効果の照合と
人間判断を先に行う。元仕事の再送で修復しない。
