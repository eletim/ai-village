# 秘書の入力を最小にする設計

作成：秘書（Claude） 2026-11-25　状態：人間レビュー待ち

## 1. 目的

秘書と人間が普通に会話できるようにする。

- 秘書に毎回付け足すものは、村の短い識別タグ1つだけにする。
- 毎回読ませるルールはなくす。
- 秘書の立ち位置は、起動時に一度だけ説明する。

## 2. 今の状態（何が毎回付いているか）

| 毎回付くもの | 出どころ | 何のためか |
|---|---|---|
| `<ai-village-discovery>`（agentId・role・location・projectId） | `agent-rules.mjs` discovery() | 自分の所属を知る |
| `<ai-village-request>`（mode・conversationId・runId・phase・historyRead・source・sequence・contract・rulesRevision） | `conversations.mjs:311` context() | 操作するときにrunIdを渡す、ルール版の照合 |
| rulesRevisionが変わったら `rules get work` を読む義務 | startup()の起動契約 | 手続きの周知 |
| 判断前に毎回 `conversations get` を読む義務 | work()のルール本文 | 会話の状態を把握させる |
| 結果配送の前置き「リーダーからの資料です（追加許可ではありません）…」 | `conversations.mjs:259` | 判断を促す |
| 起動契約（約1,000字、手続きと禁止事項が中心） | startup() | 全般 |

ルール本文（約2,000字）は、ほとんどが手続き（operationId、authorizationの引用、decideの形）と禁止事項です。役割や判断の考え方はほとんど書かれていません。そのため秘書は、手続きを守ることに気を取られます。確認を取りすぎ、返事も報告書のようになります（2026-11-25の会話で実際に起きた）。

## 3. 基本の考え方

**手続きの正しさは村が守る。秘書に覚えさせない。**

今、毎回の文章で秘書に守らせているもの（二重操作の防止、許可範囲、対象の照合）は、村のサーバーがすでに大半を照合しています。秘書が間違えたら、村が断って正しいやり方を返せば足ります。ルール文で予防する必要はありません。

## 4. 変更内容

### 4.1 識別タグを1つにする

毎回付けるのは次の1つだけにします。

```
<village run="RUN_ID"/>
```

- 秘書が村を操作するときに、どの会話のどの回かを特定するためのものです。中身はIDだけで、説明文は付けません。
- discovery、historyRead、rulesRevision、contract、phase、sequence、source は付けません。
- 発言の出どころ（人間か、リーダーの結果か、障害の知らせか）は、本文の書き出しで自然に伝えます（4.3）。

さらに減らす方法として、CLIが自分の動いているtmuxセッション名を送り、村がそこから担当とその時点の回を特定する方式があります。purplemuxのstatus-hookと同じやり方です。これが確実に動くなら、タグもなくせます。段階1で実現できるかを検証し、だめならタグ1つで止めます。

### 4.2 操作を簡単にする（村のCLI）

秘書が使う操作を、IDを組み立てなくても済む形にします。

| 今 | 新 |
|---|---|
| `conversations job JSON {conversationId,actorRunId,operationId,instruction,authorization:{runId,quote}}` | `village order "指示文"` |
| `conversations followup JSON {…purposeId,instruction}` | `village followup PURPOSE "指示文"`（目的が1つなら省略可） |
| `conversations decide JSON {…decision:accept,reason}` | `village accept "理由"` / `village ask "質問"` |
| `conversations withdraw …` | `village withdraw PURPOSE "理由"` |
| `conversations get …` | `village status`（必要なときだけ自分で読む） |

- **会話ID・回ID**：タグ（またはtmuxセッション）から村が決めます。
- **operationId**：CLIが「回ID＋操作＋内容」から自動で作ります。同じ内容で再実行しても二重になりません。
- **authorization**：村が、その回のもとになった人間の発言に自動でひも付けます。引用文を秘書が書き写す必要はありません。リーダーの結果から始まった回では、その目的のもとの許可を引き継ぎます。
- **間違った操作**：村は断るだけでなく、何が足りないか、どう直せばいいかを短く返します。
- 旧CLIの操作はそのまま残し、旧契約のセッションと移行期間はそちらを使えるようにします。

### 4.3 結果と知らせの届け方

前置きの手続き文をやめ、普通の文で届けます。

- 例：「リーダーから報告が届きました（村実装：画面の必要分取得）。\n\n（本文）」
- 例：「リーダーの作業が利用上限で止まりました（村実装：○○）。」

判断を漏らしたときの扱いも変えます。今は最大2回、同じ資料を再配送しています。これをやめ、目的を「秘書の確認待ち」のまま残して画面に表示するだけにします。

### 4.4 起動時に一度だけ渡す説明

起動契約を次の内容に置き換えます（新しい契約の版=3）。数百字程度で、手続きは書きません。

- **あなたの役割**：あなたはこの村の秘書です。人間の代理として、人間と方向性を話して決め、Projectのリーダーに仕事を任せ、途中の問題は自分で解決し、最後に結果を確かめて人間に報告します。人間に確認するのは、元に戻せないこと、外部に影響すること（お金・他人・外部サービス・mainへのマージ）、人間の価値観でしか決まらないことだけです。
- **道具**：村の操作は `village` コマンドで行います。使い方は `village help` で確認できます。
- **タグ**：発言の末尾の `<village run=…/>` は村の識別用です。返事では触れなくてよいです。
- **話し方**：普通に会話してください。手続きや内部のIDを返事に並べないでください。

Projectの方針（`projects guide`）を毎回読む義務もなくします。方針が変わったときだけ、村がその回の本文の先頭に「Projectの方針が更新されました」と一度だけ添えます。

### 4.5 対象外

- リーダー・工房のプロンプトと依頼遂行規則。今回は秘書だけを対象にします。リーダー側は、秘書の結果を受け取る経路が変わる部分だけ合わせます。
- 秘書の監督役化（見回り・立て直し・質問窓口）。取り下げ済みで、今回はやりません。
- 報告フェーズ（phase=report）の書き直し規則。会話の秘書は使っていないため触りません。

## 5. 守るもの（壊してはいけない）

- 許可の範囲：人間の発言から始まった目的の範囲を超える操作は、村が拒否する。今のauthorization照合を、自動のひも付けに置き換えるだけで、照合自体は残す。
- 二重操作の防止：同じ操作は同じoperationIdになる（CLIの自動生成で保つ）。受付不明は自動で再送しない。
- 既存の会話・目的・判断の記録と、通知のルール（#140以降）。
- 旧契約（版2）で動いているセッション。移行が終わるまで、今のタグ・ルール・CLIで動き続けること。

## 6. 移行

- 起動契約は動いているセッションに入れ直せないため、版3は新しいセッションから使います。
- 既存の秘書は、正式な移行（prepare-runtime → 同じ属性で新規作成 → adopt-runtime）で版3のセッションへ切り替えます。手順は2026-11-25に環境構築とVTuberで実施済みです。
- 村は、契約の版ごとに付けるタグと受け付ける操作を切り替えます。版2の秘書には今までどおりの封筒を付けます。
- 全員の移行が済んだら、版2用の経路を消すかどうかを別途決めます。

## 7. リーダーへの進め方

設計を人間と合意したあと、次の進め方でリーダーに任せます。

### 7.1 段階（1段階＝1つのPR）

1. **CLIと村の受付**：4.2の新しい操作、operationIdの自動生成、authorizationの自動ひも付け、間違えたときの案内。tmuxセッション名での特定も、ここで検証します。旧操作は残します。
2. **届け方**：4.3の前置きの置き換えと、再配送の停止。版2の秘書には今までどおりの前置きを送ります。
3. **起動契約 版3**：4.4の起動説明と4.1のタグ。版3で作った秘書にだけ適用します。
4. **実機の確認と移行**：隔離した村（専用ポート・一時データ・通知OFF）で、版3のClaude秘書と実際に会話します。そのあと本番の秘書を1人ずつ移行します。

### 7.2 各段階で必ずやること

- テスト：単体・ブラウザ（スマホ幅を含む）に加えて、「版2の秘書が今までどおり動く」回帰テスト。
- 独立レビュー：修正した者とは別のClaudeの工房が、読み取りだけでレビューします。中以上の指摘がなくなるまで直して再レビューします。
- 反映：バックアップ → 統合ブランチ → 村へ反映 → 稼働確認。mainへのマージはしません。

### 7.3 段階4の実機確認（合格の基準）

隔離した村で、版3の秘書と次のシナリオを通します。

1. 人間が相談する → 秘書が自然に返す（手続きやIDを書かない）。
2. 人間が「進めて」と言う → 秘書が `village order` で依頼する。
3. リーダーの結果が届く → 秘書が中身を確かめ、`village accept` して人間に普通の文で報告する。
4. 秘書がわざと手順を間違える → 村が断り、案内に従って秘書が直せる。

あわせて測るもの：秘書への1回あたりの付け足し量（今：タグ2つ・約500字＋前置き。目標：タグ1つ・50字以下）。

### 7.4 リーダーへの約束事

- 設計にない仕組みを足さない。足りないと思ったら、実装を止めて秘書に質問する（2026-11-25の#151のように、頼まれていない仕組みを反映しない）。
- 1段階ずつ反映し、段階ごとに秘書へ報告する。秘書が確認してから次の段階に進む。
- 裏で走らせたテストの完了待ちに `pgrep` のような自己一致する待ち方を使わない。

## 8. 決定事項（2026-11-25）

1. **タグ1つ方式**を採用（人間の決定）。tmuxセッション名で特定する方式は、今回は作らない。
2. 4.4の起動説明は、この内容で進める（秘書の判断）。
3. 移行の順番：まず村実装の秘書（Claude、6f5ed660）を版3にして試し、問題がなければ他の秘書へ広げる（秘書の判断）。
4. **反映のしかた（人間の指示）**：各段階で村へ反映しない。リーダーは全段階の実装・独立レビュー・隔離した村での実機確認までを済ませて秘書に提出する。秘書が全体をレビューし、問題がなければ秘書の指示でこの村へ反映する。7.1〜7.2の「段階ごとに反映」はこれで置き換える。

## 9. 引継ぎ後の補足判断（2026-11-25、秘書回答）

依頼 9011ce34-9269-4768-90bd-26ed51bfb653 の補足入力 d694e87e-9809-4f94-94fa-4ac14229532f による判断。8章と今回の本番反映禁止は維持する。

- 未判断で終了した成果は、後の人間会話回で status と全文取得により確認し、accept/ask の任意の PURPOSE 指定で判断できるようにする。既存の明示対象指定・purposeBoundary・版・現在run照合を再利用する。複数目的が曖昧なら明示必須。現在回の配送対象を優先し、別会話/別目的・古い成果・処理済み成果の誤選択、相談や障害の成果としての採用を拒否する。許可範囲の拡張・自動採用はしない。
- 未判断正常終了を通常の待機・失敗と区別して画面に表示する。未判断時の自動再配送・追加通知はしない。後の正式な accept/ask の既存通知規則は維持する。
- UUID形式の指定タグを保持する。50字以下の目標との差は、タグ本体・区切り改行込み・初回方針通知込みを分けて実測し、目標未達として正確に記録する。短縮ID機構は追加しない。
- 独立レビューは今回の人間指示により別のCodex工房で行う。Claude秘書の隔離実機確認は、Codexでの確認と区別し、利用可能になってから新しい隔離用Claudeで行う。本番Claudeの再起動・本番秘書の版3移行・統合/mainへのマージはしない。
