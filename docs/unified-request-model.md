# 共通依頼モデル

人間からの依頼もAgentからの委任も、担当者に結果を求める同じ依頼である。rootだけが状態を持つモデルを廃止し、各依頼に同じ遷移を適用する。Project、native runの終了、結果の提出、依頼の終了、外部通知は別の事実として扱う。

## 正本と互換境界

`requestGraph`（version 1）が依頼状態の正本。ノードIDは既存workIdを保持し、親ID、依頼者、担当Agent、現在run、run履歴、担当履歴、完了申告、結果版と対応判断を持つ。状態はactive（要判断の理由を含む）、submitted（結果提出済み）、completed、withdrawn。rootのhumanRequestIdは互換の依頼ツリーIDとして維持する。runModelは引き続きnative受付・実行状態の唯一の正本で、依頼側にはrunの状態を複製しない。旧requestModelは境界で生成する読取専用DTOであり保存しない。

## 遷移契約

- 作成／委任：humanまたは受付照合済みのagentがactive依頼を作る。委任は子依頼の作成であり、runはその依頼の実行。
- 観察：programが構造化されたrun事実を反映。通常の正常終了で結果を提出し、依存関係のない依頼は結果提出済みになる。人間を受け手とするrootは報告ポリシーに従い自動的に完了し、子依頼は受け手の対応によって完了する。失敗・中断・不明は結果を提出して要判断を維持する。自然文は判定に使わない。
- 子依頼のある依頼：現在runの正常終了、同runのfinish申告、全ての直接の子依頼の解決が必要。ネストにも同じ規則を適用する。子が終わっただけで親は完了しない。
- 結果への対応：結果を読む操作は不変。`respond`または`finish`の結果参照で、現在の受け手runが対応を申告する。結果ID・版・依頼の親子・主体を検証する。失敗を受け入れる判断も元のnative結果を書き換えない。
- 自動配送：提出済みで未対応の結果だけを受け手のrunとして予約する。そのrunの正常終了はその結果への対応の根拠となる。明示対応と同じ依頼遷移に収束する。予約済み・未送信なら明示対応で取消可能。送信済み／不明は履歴を保持し再送しない。
- 補足／再試行：同じ依頼の新run。過去の結果・判断・申告を消さず、新しい結果版を区別する。終端依頼への新しい目的は別依頼。
- 人間の取消／完了扱い：nativeの事実を変えず判断として保存する。通常経路で新しい受領クリックは要求しない。人間の完了扱いでも実行中の子依頼は未解決として拒否する。子がすべて終端なら、各結果を受け入れた人間の判断を依存関係にも記録して閉じる。
- 報告と通知：rootのポリシーだけが人間向け報告・外部通知を選ぶ。子には外部完了通知を作らない。外部通知の既存の永続キー・不明配送保留は維持する。

## 移行・検証・運用

`unifiedRequestVersion=1` を持つ。`unifiedData` は決定的・冪等な純粋移行で、書込前に `direct.pre-unified-requests-v1.json` を排他的に作成・fsyncする。古い形式は既存のrun/request/canonical/marker移行の後で移す。すでに新形式なら旧request/canonical/marker変換には戻さない。受付照合用のrunModel、inputCorrelation、セッション、turn、cursor、fileIdentity、補足境界、履歴、通知履歴を維持する。

旧workIdをそのまま依頼ノードIDにする。旧rootの確定状態を維持し、activeを移行だけで完了にしない。既存配送runから特定できる結果対応はそのrunを根拠に復元する。配送根拠がなければ読取・対応を推測しない。完了済みrootは再開・再配送しない。進行中runを一律不明に変更しない。参照破損は既存の隔離オーバーレイへ残し、元データを修復したことにしない。未知の版は拒否する。

移行後はrunの状態を依頼ノード内に保存しない。旧requestModelは非列挙の読取投影とHTTP DTOのみで、direct.jsonには存在しない。既存worksはCLIの識別・履歴参照用に維持し、ノードの所属・現在run・run列との一致を検査する。

## 操作と対応判断

既存 `requests delegate/get/results/finish` と短い入力タグの humanRequestId/workId/runId を維持する。humanRequestIdはツリーID、workIdは依頼ノードIDである。新しい `requests respond` は `humanRequestId,workId,runId,operationId,results` を受ける。resultsは `{requestId,resultId,version,decision:"accept"|"rework"}` の配列。主体は現在の受付照合済みrunで、直接の子依頼の最新結果だけを扱える。複数結果の一部だけを対応済みにできる。

`finish`にも同じresultsを指定できる。旧クライアントのresults省略は「その時点で利用できる直接の子結果を扱った」という従来の完了申告として受け付ける。ただし失敗結果の完了判断には明示resultsが必要。対応とnative正常終了を同一視しない。早いfinishは申告として記録するだけで、未提出の結果を未来にわたって受け入れたことにはしない。古いrunの申告は監査に残すが、現在の依存関係を消化できない。

`rework`は受け取った結果を扱ったが依存関係は未解決という判断。新しいdelegateの `replacesRequestId` に旧子依頼IDを指定すると、旧結果と判断を保持したまま新しい子依頼で依存関係を置換する。未解決の旧依頼は取り下げるが、すでに確定した完了状態は書き換えない。

人間用retry/resumeは未完了または結果提出済みの依頼に新runを追加する。省略可能な `agentId` で担当交代できる。過去runのAgentを変えず、担当履歴を保持する。完了して受け手が閉じた依頼に追加の目的があれば新しい依頼を作る。未送信の子依頼取消はroot全体を取り下げない。人間用APIの既存誤操作防止を維持する。

結果配送のqueued予約と明示対応が行き違った場合は、直前の受け手runと予約元結果が一致する場合だけ予約を撤回できる。programの `cancel-result-reservation` は未送信result専用であり、送信済み/受付不明runには使えない。送信した記録を取り消したり再送したりしない。通常の配送完了も同じhandlingに収束する。通知履歴は既存のrootキーを維持する。

規則とhelpは `agent-rules.mjs` の同一定義から生成する。起動時規則hashが変わるため、既存セッションは再起動せずlegacy全文規則へ移る。旧finishは互換維持され、すでに送ったrunの入力全文照合は変更しない。

## 反映・ロールバック（秘書が実施）

1. 対象PRを `integration/request-model` に統合し、検証済みcommitを確認する。mainにはマージしない。
2. 本番のコードと状態の世代を確認し、サービス停止中にdirect.jsonおよび通知保存ファイルの手動バックアップを同時点で取得する。Agentのnativeセッションは停止しない。
3. 検証済みコードと依存を配置し、型・構文・buildを確認してサービスを起動する。自動移行前バックアップの存在、unifiedRequestVersion、root件数、ノード数、run件数・追跡中runの照合情報、通知履歴を比較する。
4. 新規入力なしで追跡再開を確認し、既存の進行中依頼が同じrunとして継続すること、既処理結果の再配送や外部通知の再送がないことを確認する。ブラウザを再読込する。
5. 移行直後で新しい外部効果がなければ、停止してコードと状態を同時点のバックアップへ対で戻す。新しい送信・通知後は単純な巻戻しを行わない。新旧の送信事実・通知済みキーを照合して手動復旧し、受付不明の入力は再送しない。新状態を旧コードで直接開かない。

本番のコード・状態・サービスは実装担当が変更しない。移行リハーサルはread-onlyコピーで、localRun/remote/notifierを禁止するスタブ、watch:false、使い捨て状態を使う。個人情報を含むコピーは終了時に削除しコミットしない。

## 達成範囲と制約

root・子・孫に共通の依頼状態、提出結果の版、部分対応、失敗の明示判断、再作業置換、担当交代、早い申告、配送予約競合、再起動、保存失敗、報告モードとroot通知一回を対象とする。UIの内部ID入力や毎回の受領操作は増やさない。

runの受付照合、Agentの生存観察、外部通知の配送は別の状態機械を維持する。自然文から達成度は決めない。外部送信と保存を跨ぐ厳密なexactly-onceは保証しない。不明な配送を自動再送せず、監査事実と要判断を残す。同一ユーザー権限で動くAgentに対する暗号学的な本人認証は提供せず、現在run・native受付・所属を既存の境界で照合する。担当交代は既存の人間用retry/resume APIで対応し、専用の担当選択UIは追加していない。

旧形式の一般的な純粋移行テストは `state/request.ts` と `progress.ts` を引き続き検査するが、通常の依頼進行は `state/requests.ts` のみが決定する。

### 検証時の本番誤接続

再発防止としてPlaywrightの既定を専用ポート15173・一時状態・既存サーバー再利用禁止へ変更した。指定ポートが使用中なら起動に失敗し、本番を借用しない。既定設定で関連ブラウザ5件も成功した。秘書レビュー時にはこの検証事故と残存するテスト添付も確認すること。実装の本番反映とは別に扱う。
